# Auth Provider Pre-created Key Secrets Plan

## Problem

The Authentik reference deployment checks a confidential OIDC client secret
and session-encryption key into Helm templates. Both Authentik and ZITADEL also
pass a generated workload-token signing key through `helm --set-file` and let
Helm render gateway TLS private keys. Provider-internal keys are likewise
rendered from chart values.

These paths expose cryptographic material in source, rendered manifests, or
Helm release storage. The reference deployments already keep reusable local
inputs under each provider's ignored `.generated` directory. Key material
should follow that lifecycle consistently.

## Security Invariant

Helm must not receive or render cryptographic key material or confidential
OIDC credentials. Such values must be either:

- generated locally during provider preparation and provisioned before Helm;
  or
- generated by the identity provider's runtime setup and written directly to
  a Kubernetes Secret without passing through Helm.

Charts contain only Secret names and key names. Kubernetes RBAC and encryption
at rest remain deployment responsibilities.

Database passwords and published local-demo user passwords are a separate
credential-lifecycle concern and are not consolidated in this change.

## Supported Runtimes

| Runtime | Prepared material | Provider-generated material |
| --- | --- | --- |
| Authentik Compose | workload signing key, gateway TLS, Authentik secret key, OIDC client secret, session-encryption key | none |
| Authentik Kubernetes | the same logical material, provisioned as preexisting Kubernetes Secrets | none |
| ZITADEL Kubernetes | workload signing key, gateway TLS, ZITADEL master key | OIDC clients, client secrets, and session-encryption key in `nemo-zitadel-seed-state` |

The repository does not provide a ZITADEL Compose runtime.

## Generated Material

Provider preparation creates files under the provider's `.generated`
directory with `umask 077`, temporary-file writes, and atomic renames. Existing
valid files are reused so restarts do not rotate keys implicitly.

Stable provider-level material includes:

- `.generated/workload-token-private-key.pem` for each provider;
- `.generated/authentik.env` for Authentik's internal secret key;
- `.generated/user-oidc.env` for Authentik's
  `NHX_OIDC_CLIENT_SECRET` and `NHX_AUTH_SESSION_ENCRYPTION_KEY`; and
- `.generated/zitadel-masterkey` for ZITADEL's master key.

Gateway certificates are runtime-specific because Kubernetes certificates
must contain the configured Envoy Service namespace and DNS names. Compose
continues to use `.generated/gateway-tls`. Kubernetes setup stores its TLS
material under the existing per-cluster `.generated/k8s/$CLUSTER_NAME` state
directory and validates the required SANs before reusing it.

Dry-run and diagnostic output show paths and actions but never key values.

## Authentik Flow

The checked-in Authentik blueprint replaces its literal confidential-client
secret with:

```yaml
client_secret: !Env NHX_OIDC_CLIENT_SECRET
```

Compose loads the generated environment files into the services that need
them. The NeMo service receives the OIDC client and session-encryption values;
the blueprint apply service receives only the OIDC client secret; and the
Authentik services receive their internal secret key.

Kubernetes setup creates or reconciles these Secrets before Helm:

- `nemo-workload-token-signing-key`;
- `nemo-helix-envoy-tls`;
- `nemo-helix-user-oidc`; and
- the existing Secret consumed by the upstream Authentik chart for its
  internal secret key.

The Authentik umbrella chart disables key generation and references those
Secret names and keys. The blueprint apply Job maps only the OIDC client
secret into `NHX_OIDC_CLIENT_SECRET`.

## ZITADEL Flow

ZITADEL Kubernetes preparation creates or reconciles these Secrets before
Helm:

- `nemo-workload-token-signing-key`;
- `nemo-helix-envoy-tls`; and
- `zitadel-masterkey`.

The chart disables the corresponding key generation and only references the
preexisting Secrets.

ZITADEL owns confidential OIDC client-secret generation. Its seed Job will
continue to create the OIDC applications through the ZITADEL API and write the
returned client secrets plus a generated session-encryption key directly to
`nemo-zitadel-seed-state`. That Secret is not a Helm-rendered resource, and its
values must not be moved into local files or Helm values.

## Kubernetes Provisioning

Each runner will ensure the namespace exists, generate runtime-specific TLS
material, and reconcile the required Secrets before invoking Helm. Secret
creation uses file-based `kubectl create secret --dry-run=client -o yaml`
piped directly to `kubectl apply -f -`; values do not appear in command
arguments or logs.

The manual tutorials use the same ordering and files. A Helm invocation on its
own requires the documented preexisting Secrets and fails visibly when a
referenced Secret or key is absent.

Rotation is explicit: replace the generated file, reconcile its Kubernetes
Secret, reapply provider configuration when necessary, and restart consumers.
Preparation never rotates stable material as a side effect of an upgrade.

## Helm Changes

Both provider charts set workload-token signing and gateway TLS generation to
disabled and remove the `--set-file` signing-key path. Secret-producing
templates for those keys are removed from the umbrella charts.

The Authentik chart also removes the OIDC Secret template and all literal OIDC
credential values. The ZITADEL generated-secret template stops owning the
master key. Existing configuration fields retain Secret names and key names so
pods and jobs consume the precreated objects without inline values.

## Verification

Static and render tests verify that:

- preparation creates required files with restrictive permissions and reuses
  them;
- dry-run output contains no secret values;
- Authentik Compose injects each key only into its required services;
- Kubernetes runners provision Secrets before Helm for both providers;
- the Authentik blueprint uses `!Env` and contains no OIDC secret literal;
- provider Helm output contains no signing key, TLS private key, provider
  internal key, Authentik OIDC secret, or session-encryption key;
- charts reference the expected preexisting Secret names and keys;
- ZITADEL OIDC and session secrets remain seed-Job-generated; and
- existing Authentik Compose/Kubernetes and ZITADEL Kubernetes contract tests
  continue to pass.

Focused live verification covers Authentik Compose, Authentik Kubernetes, and
ZITADEL Kubernetes. There is no ZITADEL Compose verification target.
