| Release-note coverage | `Missing — no docs/about/release-notes/release-0-11-0.mdx at the release SHA` |

**Description**

A Job is `creation_pending` while its resources are prepared and becomes `created` only after setup is durable. Deletion records `deletion_pending`, returns HTTP 204, and the Jobs controller finishes resource cleanup before it removes the Job. `jobs.storage.creation_timeout_seconds` (default 900) sets how long unfinished creation waits before it becomes eligible for automatic cleanup. Continuing SDK handles keep the Job ID they received.

**User impact**

Operators and SDK users who poll or delete Jobs. Clients that treat HTTP 204 from delete as immediate removal must poll get by Job ID until it returns not found.

#### CLI validation

The documented status values for `nemo jobs steps update-status` and `nemo jobs tasks create-or-update` now include `creation_pending` and `deletion_pending`. The documentation has no dedicated delete-and-poll CLI sequence.

```sh
nemo jobs list
```

Expected:

- A newly submitted Job briefly shows `creation_pending` and then `created`.
- After delete returns HTTP 204, get by the returned Job ID eventually returns not found.

#### Additional validation

- Recreate a Job under the name of a deleted Job; an existing SDK handle or watch keeps following the original Job ID.
- Deleting a legacy Job without an allocation receipt retains its unverified Fileset for reconciliation, as documented.
- A caller-supplied output location is borrowed and is not deleted with the Job.
- Upgrade: confirm that in-flight Jobs from 0.10.0 are reconciled after upgrade. Needs clarification.

#### Draft release-note text

Withheld from **Draft release notes**: release-note coverage is Missing. Proposed text for the release-notes author: Jobs report `creation_pending` while setup completes and `deletion_pending` while cleanup runs; delete returns HTTP 204 and the Job is removed after cleanup.

**Description**

**User impact**

CLI users can select large task ranges and recover from an ambiguous submit without re-importing the source.

#### CLI validation

```sh
TASKSET_INFO="$(nemo evals tasksets create --workspace "$WS" --harbor-hub datacurve/deep-swe \
  --tasks anko-default-function-arguments,geo-shapeindex-serialization --json)"
TASKSET="$(printf '%s\n' "$TASKSET_INFO" | jq -er '.taskset_ref')"
INTAKE_DATASET="$(printf '%s\n' "$TASKSET_INFO" | jq -er '.intake_dataset')"
nemo evals runs tasks "$RUN_ID" --workspace "$WS" --phase failed --page-size 1000
nemo evals runs submit --workspace "$WS" --taskset "$TASKSET" --agent oracle \
  --experiment harbor-runs --intake-dataset "$INTAKE_DATASET" --idempotency-key '<original key>'
```

Expected:

- `--tasks 0-4,7,<name>` selects indexes 0 through 4, index 7, and the named task.
- A range endpoint that doesn't exist, a start greater than the end, or a repeated task (including through overlapping ranges) is an error.
- Resubmitting with the original idempotency key and settings does not start a duplicate run.
