<a id="ft-create-customization-job"></a>

Customization jobs are submitted to one of two backends. Choose the backend that matches your hardware and training goal, then build that backend's job spec and submit it. For the full per-backend hyperparameter reference, see [Training Configuration](/documentation/customizer-reference/manage-customization-jobs/training-configuration).

| Backend | Best for | Methods |
|---------|----------|---------|
| **Automodel** (default) | Production fine-tuning, larger models, multi-GPU scaling | SFT, distillation; LoRA, merged-LoRA, or full-weight |
| **Unsloth** | Memory-constrained single-GPU training | SFT; LoRA with optional 4-bit / 8-bit loading, or unquantized full-weight |

## Prerequisites

Before you can create a customization job, make sure that you have:

- Configured a CLI context that points at your NeMo Helix deployment. Refer to [Connect with CLI Contexts](/documentation/reference/cli-reference/connect-to-deployments).
- Created a [FileSet and Model Entity](/documentation/customizer-reference/manage-model-entities/overview) for your base model.
- [Uploaded a dataset](/documentation/get-started/core-concepts/manage-files) as a FileSet.
- Determined the [training configuration](/documentation/customizer-reference/manage-customization-jobs/training-configuration) you want to use for the customization job.
- Verified that the platform has sufficient storage for the job. Budget against the downloaded base checkpoint size: Full SFT jobs require approximately 3× in free disk space, and LoRA jobs require approximately 1.5×. See [ft-tut-understand-models](/documentation/customizer-reference/tutorials/understanding-models-and-training) for details. Include any retained deployment copies separately.

## Submit an Automodel Job

Build an `AutomodelJobInput` spec and submit it to the `automodel` backend. The job runs on the platform's GPU cluster, and `create()` returns a handle you can use to poll its status.

```python
from nemo_helix_plugin.client.client import NemoClient
from nemo_customizer.sdk import Customization
from nemo_automodel_plugin.schema import AutomodelJobInput

# Initialize the client
client = NemoClient.from_config()
customization = Customization.from_client(client)

# Build the job spec (SFT + LoRA)
spec = AutomodelJobInput(
    model="default/nemotron-3-5-lightning-30b-a3b",  # Base Model Entity (workspace/name)
    dataset={"training": "default/my-training-dataset"},
    training={
        "training_type": "sft",
        "finetuning_type": "lora",
        "lora": {"rank": 16, "alpha": 32, "exclude_modules": ["*.out_proj"]},
        "max_seq_length": 2048,
    },
    schedule={"epochs": 3},
    batch={"global_batch_size": 8, "micro_batch_size": 1},
    optimizer={"learning_rate": 1e-5},
    parallelism={"num_gpus_per_node": 4, "expert_parallel_size": 4},
    output={"name": "my-custom-model"},  # Optional: auto-generated if omitted
)

# Submit the job
job = customization.automodel.jobs.create(spec=spec, workspace="default", name="my-lora-job")

print(f"Submitted job: {job.job.name}")
print(f"Job status: {job.job.status}")
```

<Markdown src="/snippets/_snippets/tutorials/default-workspace-note.mdx" />

The LoRA values follow Automodel's reference recipe for this architecture. To start from the recipe for another model, see [Start from a Reference Recipe](/documentation/customizer-reference/manage-customization-jobs/training-configuration#reference-recipes).

The response preserves the explicit `name`. If you omit `name`, the platform generates a backend-prefixed job name.

## Submit an Unsloth Job

The Unsloth backend runs on a single GPU and supports 4-bit / 8-bit quantized loading for LoRA. Full-weight training requires `model.load_in_4bit=false` and `model.load_in_8bit=false`. Build a `UnslothJobInput` spec and submit it to the `unsloth` backend. Note that Unsloth uses its own field names (`model.name`, `dataset.path`, `batch.per_device_train_batch_size`).

```python
from nemo_helix_plugin.client.client import NemoClient
from nemo_customizer.sdk import Customization
from nemo_unsloth_plugin.schema import UnslothJobInput

client = NemoClient.from_config()
customization = Customization.from_client(client)

spec = UnslothJobInput(
    model={"name": "default/qwen3-1.7b", "load_in_4bit": True},
    dataset={"path": "default/my-training-dataset", "apply_chat_template": True},
    training={"finetuning_type": "lora", "lora": {"rank": 16, "alpha": 16}},
    schedule={"epochs": 3},
    batch={"per_device_train_batch_size": 2, "gradient_accumulation_steps": 4},
    optimizer={"learning_rate": 2e-4},
    output={"save_method": "lora"},
)

job = customization.unsloth.jobs.create(spec=spec, workspace="default", name="my-unsloth-lora-job")

print(f"Submitted job: {job.job.name}")
```

## Knowledge Distillation (Automodel)

Knowledge distillation is an Automodel feature. Set `training.training_type` to `"distillation"` and provide a `teacher_model` that references a second Model Entity. The `model` field is the student model being trained.

```python
from nemo_helix_plugin.client.client import NemoClient
from nemo_customizer.sdk import Customization
from nemo_automodel_plugin.schema import AutomodelJobInput

client = NemoClient.from_config()
customization = Customization.from_client(client)

spec = AutomodelJobInput(
    model="default/qwen3-0.6b",  # Student model
    dataset={"training": "default/my-training-dataset"},
    training={
        "training_type": "distillation",
        "finetuning_type": "lora",
        "teacher_model": "default/qwen3-8b",  # Teacher model
        "teacher_precision": "bf16",
        "distillation_ratio": 0.5,
        "distillation_temperature": 2.0,
    },
    schedule={"epochs": 2},
    batch={"global_batch_size": 64, "micro_batch_size": 1},
    optimizer={"learning_rate": 5e-5},
    parallelism={"num_gpus_per_node": 1},
)

job = customization.automodel.jobs.create(spec=spec, workspace="default", name="my-kd-job")
```

<Note>

See [Knowledge Distillation constraints](/documentation/customizer-reference/manage-customization-jobs/training-configuration#kd-constraints) for requirements on model compatibility, tokenizer, and GPU memory.

</Note>

## Check a Job Before Submitting

A dry run checks a job the way submit does, then stops before creating it. It validates and compiles the job, checks that its execution profile exists, and checks the first 10 rows of each dataset file training reads with the backend's own validator. A failed row check names the file and line, so a dataset error is found before the job is scheduled. A dry run creates nothing.

Pass `dry_run=True` to `create`. It is the same call as a submit, with `?dry_run=true` on the request. When every check passes, it returns the job it would create, unsaved (no `id` or `status`), with the checks in `status_details["checks"]`. When a check fails, it raises `UnprocessableEntityError` (HTTP 422), whose body lists every check, passed and failed:

```python
from nemo_helix_plugin.client.errors import UnprocessableEntityError

try:
    job = customization.automodel.jobs.create(spec=spec, workspace="default", dry_run=True).data()
    checks = job.status_details["checks"]
except UnprocessableEntityError as error:
    checks = error.body["detail"]["checks"]
for check in checks:
    print("OK  " if check["passed"] else "FAIL", check["name"], check["message"])
```

From the CLI, add `--dry-run` to the submit command. It exits non-zero when a check fails:

```bash
nemo customization automodel --job-json job.json --dry-run
```

With `--upload-model`, `--upload-dataset` or `--upload-environment`, the dry run uploads nothing and runs on your machine. It checks the job JSON and, with `--upload-dataset`, the first 10 rows of the local dataset. The model and dataset references and the execution profile do not exist yet, so submit checks them after the upload.

Before preparing any data, run `nemo jobs list-execution-profiles` to check that the platform is reachable and has a GPU execution profile (`provider` is `gpu` or `gpu_distributed`) for the backend. For `rl`, that profile's `backend` must be `kubernetes_job` or `volcano_job`.

## After Submission

A submitted job runs on the platform's Jobs service. Manage its lifecycle — polling status, listing, cancelling, pausing, resuming, and rerunning — through that service, regardless of which backend you submitted to. See [Get Job Status](/documentation/customizer-reference/manage-customization-jobs/get-job-status), [List Active Jobs](/documentation/customizer-reference/manage-customization-jobs/list-active-jobs), [Cancel a Job](/documentation/customizer-reference/manage-customization-jobs/cancel-job), and [Pause, Resume, and Rerun a Job](/documentation/customizer-reference/manage-customization-jobs/pause-resume-rerun).

For field-level details of the job spec and W&B or MLflow integration options, see [Customization Job Reference](/documentation/customizer-reference/manage-customization-jobs/customization-job-reference).

## Training Output

When training completes, the system automatically uploads the trained artifacts to a new FileSet (`output.fileset`) and creates an output based on the fine-tuning regime:

| `training.finetuning_type` | Output Created |
|----------------------------|----------------|
| `lora` | **Adapter** attached to the parent Model Entity |
| `lora_merged` | **New Model Entity** with the adapter merged into the base weights |
| `all_weights` | **New Model Entity** with all model weights (complete fine-tuned model) |

### LoRA Adapters

For LoRA jobs, the adapter is added to the parent Model Entity's `adapters` list:

```python
# After training completes, retrieve the model to see the adapter
model = client.models.get_model(workspace="default", name="nemotron-3-5-lightning-30b-a3b").data()

for adapter in model.adapters or []:
    print(f"Adapter: {adapter.name}")
    print(f" Fileset: {adapter.fileset}")
    print(f" Enabled: {adapter.enabled}")
```

Adapters are enabled by default and are automatically loaded by NIMs serving this model with LoRA support.
