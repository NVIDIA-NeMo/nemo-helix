<a id="eval-metrics-similarity"></a>

NeMo Helix offers [built-in metrics](/documentation/evaluate-models/metrics) that can be configured to evaluate on your custom data. Similarity metrics compare generated or precomputed text against references, labels, or numeric/string expectations. They support Jinja templates so you can map your dataset columns to the values each metric evaluates.

Template functionality provides maximum flexibility for evaluating your models on proprietary, domain-specific, or novel tasks. You can bring your own datasets, define your own prompts and templates using [Jinja](https://github.com/pallets/jinja), and select the metrics that matter most for your use case. This approach is ideal when:

- You want to evaluate on tasks, data, or formats not covered by industry benchmarks or built-in metrics.
- You need to measure model performance using custom or business-specific criteria.
- You want to experiment with new evaluation methodologies, metrics, or workflows.
- You need to create custom prompts and templates for specific use cases.

## Setup

```python
from nemo_evals.sdk import Evaluator
from nemo_helix_plugin.client.client import NemoClient

client = NemoClient.from_config()
evaluator = Evaluator.from_client(client)
```

Use `evaluator.submit(metric=metric, dataset=dataset)` for a durable platform job. For local in-process iteration without the platform, use `nhx_evals_sdk.Evaluator` directly:

```python
job = evaluator.submit(metric=metric, dataset=dataset)
job.wait_until_done()
result = job.get_result()
```

## Template Variables

All similarity metrics support Jinja templating with these variables:

- `{{item}}` - Access dataset columns (e.g., `{{item.question}}`, `{{item.answer}}`)
- `{{sample.output_text}}` - The model's generated output for online runs
- Jinja filters: `lower`, `upper`, `trim`, `replace`, etc.

Use Jinja filters to normalize text before comparison:

```python

from nhx_evals_sdk import ExactMatchMetric
metric = ExactMatchMetric(
    reference="{{item.expected | lower | trim}}",
    candidate="{{item.output | lower | trim}}",
)
```

## BLEU Metric

BLEU (Bilingual Evaluation Understudy) measures the similarity between machine-generated text and reference translations by comparing n-gram overlap. It's commonly used for evaluating machine translation and text generation tasks.

**Use BLEU when:**
- Evaluating machine translation quality
- Measuring text generation similarity to references
- Comparing multiple reference texts

**Metric Output:** A score between 0 and 100, where 100 indicates perfect match with references.

<Tabs>

<Tab title="Local Evaluation">

```python
from nhx_evals_sdk import Evaluator as LocalEvaluator

from nhx_evals_sdk import BLEUMetric

metric = BLEUMetric(
    references=["{{item.reference_1}}", "{{item.reference_2}}"],
    candidate="{{item.model_output}}",
)

result = LocalEvaluator().run_sync(
    metrics=[metric],
    dataset=[
        {
            "reference_1": "The cat sits on the mat.",
            "reference_2": "A cat is sitting on the mat.",
            "model_output": "The cat is on the mat.",
        },
        {
            "reference_1": "Hello world!",
            "reference_2": "Hi world!",
            "model_output": "Hello world!",
        },
    ],
)

for score in result.aggregate_scores.scores:
    print(f"{score.name}: mean={score.mean}")
```

</Tab>

## Exact Match Metric

Exact Match compares the candidate text with the reference text for perfect equality. This metric returns 1 if the strings match exactly and 0 otherwise.

**Use Exact Match when:**
- Evaluating classification tasks with discrete labels
- Checking for exact answer correctness
- Validating structured output formats

**Metric Output:** Binary score (0 or 1).

<Tabs>

<Tab title="Local Evaluation">

```python
from nhx_evals_sdk import Evaluator as LocalEvaluator

from nhx_evals_sdk import ExactMatchMetric

metric = ExactMatchMetric(
    reference="{{item.correct_answer | lower | trim}}",
    candidate="{{item.model_answer | lower | trim}}",
    description="Exact match for question answering",
)

result = LocalEvaluator().run_sync(
    metrics=[metric],
    dataset=[
        {"correct_answer": "Paris", "model_answer": "Paris"},

        {"correct_answer": "Berlin", "model_answer": "Munich"},
```

## F1 Metric

F1 measures token-level overlap between candidate and reference text. It balances precision and recall, making it useful when there are multiple acceptable ways to phrase a response.

**Use F1 when:**
- Evaluating extractive question answering
- Comparing short free-form answers
- Measuring partial matches where exact match is too strict

**Metric Output:** A score between 0 and 1.

## Finance QA Metric

Finance QA scores answers to financial document questions the way the [Nemotron finance LoRA cookbook](https://github.com/NVIDIA-NeMo/Nemotron/tree/main/usage-cookbook/Nemotron-3.5-Super-VL/lora-finance) does, so its scores match the cookbook's `evaluation.py` row for row. The prediction is the text after the first `</think>`, and the reasoning trace is the text before it.

**Use Finance QA when:**
- Scoring TAT-DQA or BizBench (`CodeFinQA`, `CodeTAT-QA`) questions, for example after fine-tuning on the cookbook's data
- Reproducing the cookbook's accuracy and F1 figures

**Metric Output:** Several scores per row:

| Score | Value |
|-------|-------|
| `exact` | The prediction equals the reference after Unicode (NFKC) normalization, case folding, collapsing whitespace, and stripping `.,;:!?` from both ends. |
| `relaxed` | When both parse as numbers (ignoring `,`, `$`, `€`, and `£`): within `tolerance` relative error (default 0.05), and in the same scale (`%`, `percent`, `thousand`, `million`, `billion`) when the reference has one. Otherwise `exact`. |
| `task_correct` | For `multi-span` tasks, the same spans in any order, split on a pipe, `##`, or `;`. For `span` tasks, `exact`. For other tasks, `relaxed`. |
| `answer_f1` | For `span` and `multi-span` tasks, token F1. For other tasks, `relaxed` as 1 or 0. |
| `trace_closed` | The completion contains `</think>`. |
| `program_syntax_valid` | Only for `program_synthesis_tasks` (default `CodeFinQA` and `CodeTAT-QA`): the reasoning trace parses as Python. It is parsed, never run. |
| `hit_max_new_tokens` | Only when `max_new_tokens` is set and the response reports usage: the completion used all `max_new_tokens` tokens. Its aggregate `sum` is the number of rows that did. |
| `task` | The row's task, as a label. It isn't aggregated. |

The `task` template selects how each row is scored. It must render a task name such as `TAT-DQA/span`, `TAT-DQA/multi-span`, `TAT-DQA/arithmetic`, `TAT-DQA/count`, or `CodeFinQA`. For online evaluations, omit `candidate`: the metric rebuilds the completion from the response's `reasoning_content` (or `reasoning`) and `content`. To score as the cookbook does, enable thinking, use temperature 0, set `max_new_tokens` to the request's `max_tokens`, and leave `reasoning` unset in the run config, because its `end_token` handling rewrites the response the metric reads.

## Number Check Metric

Number Check performs numerical comparisons and operations on extracted values. Supports equality, inequality, comparison operators, and absolute difference calculations.

**Use Number Check when:**
- Validating numerical outputs (calculations, counts, scores)
- Checking value ranges or thresholds
- Comparing predicted vs expected numbers

**Metric Output:** 1 if the condition is true, 0 otherwise. If either value cannot be parsed as a number, the row score is `NaN`. The metric reads the last number in each value, and a last number with a comma between digits (`1,000`) or in scientific notation (`6.02e23`) counts as unparseable.

**Large Numbers:**

- Integers are compared exactly up to Python's [integer string conversion limit](https://docs.python.org/3/library/stdtypes.html#int-max-str-digits), 4,300 digits by default. Leading zeros don't count toward the limit for this metric.
- Integers with more digits, and decimals beyond the floating-point range (about 1.8e308), are compared as positive or negative infinity. Two different values that become the same infinity compare as equal (for example, `equals` scores 1), but their `absolute difference` is `NaN`, so that operation scores 0.
- Each operand outside the floating-point range adds a diagnostic to the row that names the operand (`left` or `right`).
- Disabling the limit, for example with `PYTHONINTMAXSTRDIGITS=0` in the process that runs the evaluation, removes the integer cutoff.

### Supported Operations

- Equality: `"equals"`, `"=="`
- Inequality: `"!="`, `"<>"`, `"not equals"`
- Comparisons: `">"`, `"gt"`, `">="`, `"gte"`, `"<"`, `"lt"`, `"<="`, `"lte"`
- Absolute difference: `"absolute difference"` (requires `epsilon` parameter)

## ROUGE Metric

ROUGE (Recall-Oriented Understudy for Gisting Evaluation) measures overlap between generated text and reference text. It is commonly used for summarization and long-form generation quality checks.

**Use ROUGE when:**
- Evaluating summarization quality
- Measuring overlap with reference passages
- Comparing generated text against longer expected answers

**Metric Output:** ROUGE-1, ROUGE-2, ROUGE-3, and ROUGE-L F1 scores between 0 and 1.

## Sequence Similarity Metric

Sequence Similarity scores how closely the candidate matches the reference, character by character. The score is Python's `difflib.SequenceMatcher(None, candidate, reference).ratio()`: twice the number of matching characters, divided by the total length of both strings.

**Use Sequence Similarity when:**
- Giving partial credit for long structured outputs, such as tagged or JSON extractions, where exact match is too strict
- Reproducing scores that a recipe or paper reports as a `difflib` ratio

**Metric Output:** A score between 0 and 1, where 1 means the strings are identical.

The metric doesn't normalize text, so case and whitespace count. Use Jinja filters in the templates, such as `trim`, to normalize before comparison. The argument order is fixed (candidate first) because it can change the score: once the reference is 200 characters or longer, `SequenceMatcher` ignores characters that make up more than 1% of it.

<Tab title="Local Evaluation">

```python
from nhx_evals_sdk import Evaluator as LocalEvaluator

    reference="{{item.label}}",
    candidate="{{item.prediction | trim}}",
)

    metrics=[metric],
    dataset=[
        {
            "label": "<s_nm>ICED TEA</s_nm><s_cnt>2</s_cnt><s_price>18,000</s_price>",
```

## String Check Metric

String Check performs various string operations and comparisons. Supports equality, containment, and prefix/suffix checks.

**Use String Check when:**
- Validating text format or structure
- Checking for keyword presence
- Pattern matching in generated text
- String-based classification

**Metric Output:** Binary score (1 if condition is true, 0 otherwise).

### Supported Operations

- Equality: `"equals"`, `"=="`
- Inequality: `"!="`, `"<>"`, `"not equals"`
- Containment: `"contains"`, `"not contains"`
- Pattern: `"startswith"`, `"endswith"`

## Dataset Format

The examples on this page use inline dataset rows with `dataset=[...]`. Template fields determine the columns required by each metric:

- `reference`, `references`, `left_template`, and `right_template` read from `item` fields in the dataset.
- `candidate` reads from an `item` field for offline rows when configured.
- If `candidate` is omitted for BLEU, Exact Match, F1, ROUGE, or Sequence Similarity, the metric uses `sample.output_text`, which is populated during online evaluations.
- Finance QA also reads its `task` template from `item` fields. If its `candidate` is omitted, it uses the model response, or `sample.output_text` when there is no response.

Keep field names consistent between the dataset rows and the templates you configure. For example, `{{item.expected}}` requires each row to include an `expected` field.
