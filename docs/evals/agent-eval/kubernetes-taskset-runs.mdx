description: "Select Harbor tasks, build their images, submit independent task Jobs, and inspect or publish their results."

Use `nemo evals runs` to evaluate a Harbor task suite on a configured Kubernetes deployment. Submission publishes the selected tasks and a taskset, freezes their revisions and execution settings, and returns a durable run ID. Each task runs in its own Jobs Service Job and uses OpenSandbox for its environment. A final bundle combines the task results.

This is different from the [local Harbor runner](/documentation/evaluate-models/agent-eval/harbor-runner), which uses Docker on the runner host. The commands below submit work to your connected deployment; they do not configure Kubernetes or start a local platform.

## Prerequisites

- Connect the 0.9 CLI to the intended deployment and workspace using [CLI contexts](/documentation/reference/cli-reference/connect-to-deployments). The examples use `default`; change `--workspace` consistently if needed.
- Have the Evals plugin and its Harbor dependencies available in the CLI environment. Remote Hub imports need Harbor's registry access; Git imports also need `git` on `PATH` and access to the public repository.
- Ask the deployment operator to confirm the following before submitting:
  - Evals, Files, Jobs, and image-builder services and their required controllers are enabled, with working artifact storage and an image registry accessible to build jobs and sandboxes.
  - `evals.runs.harbor` is configured. It is unset by default, which disables Kubernetes taskset runs. Its `dispatcher_image` must be digest-pinned and contain the Evals dispatcher and Harbor OpenSandbox environment. `dispatcher_profiles` must name allowed Kubernetes Jobs profiles, not host-subprocess profiles.
  - `sandbox_profiles` and `default_sandbox_profile` are configured, with the platform's OpenSandbox server connection and API-key injection working. The profile controls egress, resource ceilings, and sandbox lifetime. See [OpenSandbox deployment](/documentation/kubernetes-deployment/setup/helm/open-sandbox) and the [configuration reference](/documentation/kubernetes-deployment/config-reference).
  - Your identity can publish tasks/tasksets, request image builds, and submit Jobs in the workspace. For Intake publication, it also needs access to the Experiment and permission to create Evaluations.

<Warning>

A successful submission is not proof that image pulls, sandbox scheduling, verifier execution, network isolation, or Intake publication work on your cluster. Start with one trusted CPU task and inspect its results before scaling up. Harbor task packages include executable build, solution, and verifier code; only submit packages you trust.

</Warning>

## Select tasks before uploading

Prepare a local Harbor dataset directory containing complete task packages (`task.toml`, `instruction.md`, an environment, tests, and a solution if using the `oracle` agent). See [Harbor tasks](https://www.harborframework.com/docs/tasks) for the format.

For a small CPU example from a source checkout, run the following from the repository root. This copies the bundled hello-world suite into a new temporary directory without changing the checkout:

```bash
SUITE_DIR="$(mktemp -d)/hello-world-suite"
cp -R packages/nhx_evals_sdk/examples/harbor/hello_world_dataset "$SUITE_DIR"
nemo evals runs submit --workspace default --harbor-dir "$SUITE_DIR" --list-tasks
```

Outside a source checkout, set `SUITE_DIR` to your own complete Harbor dataset directory instead. `--list-tasks` prints selectable tasks and exits before uploading or building. Selection uses zero-based indexes or task names, separated by commas. For example, `--tasks '0'` selects the first task; `--tasks '0,2'` selects two. Use the names printed for your dataset, not names from another suite.

As alternatives to `--harbor-dir`, you can select from one remote source:

- `--harbor-hub 'org/dataset@ref'` downloads tasks from Harbor Hub.
- `--harbor-git 'https://github.com/org/repo.git@tag-or-commit'` reads `tasks/` from a public Git repository. The ref must be a tag or commit, not a moving branch. To select another directory, use a GitHub tree URL of the form `https://github.com/org/repo/tree/tag-or-commit/path/to/tasks`.

Replace the remote identifiers with a real dataset and immutable version you have reviewed. Add `--list-tasks` first, then repeat the same source with `--tasks` to submit a subset. Source flags are mutually exclusive. A Git import records the resolved commit, not just the supplied tag.

## Build images and submit a run

For the local hello-world suite above:

```bash
nemo evals runs submit \
  --workspace default \
  --harbor-dir "$SUITE_DIR" \
  --tasks '0' \
  --agent oracle \
  --cpus 1 --memory-mb 2048 --storage-mb 10240 \
  --idempotency-key hello-world-check-1
```

`oracle` runs the task's supplied solution; it is an infrastructure check, not a measure of model quality, and this example needs no model API key or GPU. Other agents may need model access, secrets, and profile-approved network destinations; configure their Harbor target in a [request file](#use-a-request-file) rather than putting credentials in command lines.

By default, submission:

1. Uploads the selected packages as stored tasks and publishes a taskset containing only those revisions.
2. Requests image builds and waits for them to become ready. Prebuilt images also go through the platform's image preparation/copy path. A failed build stops this CLI submission; fix the reported cause before retrying.
3. Submits the pinned taskset and target, then prints `Run <run-id> accepted` and a status command. Copy the actual run ID from this output.

`--poll-seconds` controls image-build polling, not task concurrency. `--no-build-images` skips the CLI's build request/wait loop, but is **not** a way to disable image preparation: server submission starts a first build when a task has none.

An idempotency key is scoped to the workspace and caller. Retry the **same request** with the same key after an ambiguous submit failure; it returns the accepted run instead of intentionally starting another. A changed request with an existing key conflicts. Use a new key for an intentional new run, and keep the local source unchanged when retrying. The key does not undo task uploads or image builds that precede acceptance.

### Size sandboxes and limit concurrency

`--cpus`, `--memory-mb`, and `--storage-mb` override each task's agent-sandbox resources. A separate verifier retains the task's own resource settings. `--sandbox-profile` selects an operator-defined sandbox profile; `--dispatcher-profile` selects an allowed Jobs profile for the dispatcher task Jobs. These are different controls: dispatcher resources are not the agent sandbox's resources.

Overrides must be positive integers and within the profile's ceilings; requests that exceed them fail validation rather than grant extra resources. Without overrides, task environment settings apply, with fallback CPU/memory defaults where absent. Ask the operator for valid profile names and limits; do not assume a profile named in another deployment exists on yours.

To cap the number of task Jobs running at once or set a run timeout, use `execution.max_concurrent_task_jobs` and `timeout_seconds` in a request file. Trials within each task Job run serially; do not set `spec.target.n_concurrent_trials` for this path. Run timeouts are bounded by the operator's `evals.runs` settings and count from acceptance, including time waiting for execution.

## Use a request file

Save this as `harbor-run.json`. It uses the deterministic `oracle` target and leaves profile names to the deployment defaults:

```json
{
  "spec": {
    "target": {
      "kind": "harbor",
      "source": {"name": "oracle"}
    }
  },
  "execution": {
    "kind": "harbor-task-jobs",
    "max_concurrent_task_jobs": 2,
    "sandbox": {"cpus": 1, "memory_mb": 2048, "storage_mb": 10240}
  },
  "timeout_seconds": 3600
}
```

Submit it with a dataset source, which supplies `spec.tasks`:

```bash
nemo evals runs submit --workspace default \
  --harbor-dir "$SUITE_DIR" --tasks '0' \
  --spec-file harbor-run.json --idempotency-key hello-world-spec-1
```

With `--spec-file`, put sandbox and dispatcher settings in `execution`; `--agent` and `--dispatcher-profile` do not override the file, and sandbox CLI overrides are rejected. For a model-backed Harbor agent, replace `spec.target` using the [Harbor target fields](/documentation/evaluate-models/agent-eval/harbor-runner#platform-plugin) and your approved secret references.

You can also omit the dataset source and set `spec.tasks` in the JSON to an existing stored taskset reference, such as `default/my-suite` or `default/my-suite#<revision>`, after replacing those names with your own. Use [Manage Tasks & Tasksets](/documentation/evaluate-models/manage-tasks-tasksets) to publish or inspect stored tasksets through the SDK. The CLI resolves the stored taskset, optionally narrows it with `--tasks`, and creates a pinned selection taskset for the run. Kubernetes requests require a stored taskset reference and a Harbor target, not inline tasks or precomputed trials.

## Publish to an Intake Experiment

Create an Experiment once, or use an existing one in the same workspace:

```bash
nemo experiments create harbor-checks --workspace default \
  --description "Harbor infrastructure checks" --exist-ok
```

Add `--experiment harbor-checks` when submitting:

```bash
nemo evals runs submit --workspace default \
  --harbor-dir "$SUITE_DIR" --tasks '0' --agent oracle \
  --experiment harbor-checks --idempotency-key hello-world-intake-1
```

The run creates one Evaluation named after the run in that Experiment. Task Jobs publish their trials as they finish. Find it in [Studio Experiments](/documentation/studio/experiments) and compare results using the [Experiments workflow](/documentation/evaluate-models/experiments).

For local sources the Evaluation's dataset defaults to the taskset name and revision. Hub/Git submissions with `--experiment` record the source dataset and version/resolved commit. In a request file, use top-level `publication.intake` for `experiment` and optional `agent_name`, `dataset_name`, and `dataset_version`. Do not use `spec.publication`: it is rejected for Kubernetes runs. `--experiment` replaces the file's publication settings.

## Inspect progress and collect results

Set `RUN_ID` to the ID printed by submission, then inspect the same workspace:

```bash
RUN_ID='replace-with-the-accepted-run-id'
nemo evals runs list --workspace default --mine --active
nemo evals runs status "$RUN_ID" --workspace default --watch
nemo evals runs results "$RUN_ID" --workspace default --json
nemo evals runs download "$RUN_ID" --workspace default --output-dir ./harbor-results
```

`status` shows task Jobs and the result-bundle Job. `results` shows available per-task scores and a rollup; results can still be partial while work is in progress. `download` retrieves the merged `agent-eval-results/` bundle, including `report.html` and `summary.json`, once it is ready. A terminal execution phase alone does not mean the bundle is available: inspect `result_state` in `status --json` and any bundle errors. See [Reading Results](/documentation/evaluate-models/agent-eval/reading-results) for bundle interpretation.

### Diagnose failures before scaling up

| Symptom | Next check |
| --- | --- |
| Kubernetes runs are not configured, or profile rejected | Have the operator check `evals.runs.harbor` and its allowed Kubernetes dispatcher/sandbox profiles. |
| Image build fails | Read the task/revision and error reported by submission; check the package's Dockerfile or prebuilt image and registry/build access. Do not bypass the failure by assuming the task image is ready. |
| Task Job or sandbox does not start | Inspect the Job shown by `status`, cluster scheduling/image-pull events, OpenSandbox connectivity, storage, and requested resources with the operator. |
| Agent setup or model calls fail | Check secret access and the profile's setup/agent egress policy. Do not loosen isolation merely to make a run pass. |
| Submit reports a server error after acceptance may have occurred | Retry the identical command with its original idempotency key, not a new key. |
| Scores exist but publication or download is unavailable | Inspect `status --json`, task publication state in `results --json`, and bundle errors separately. Check Intake permissions/availability and result storage. |

Run completion, score correctness, Intake visibility, and enforced sandbox boundaries are separate acceptance checks. Validate them on the intended deployment; this guide does not establish cluster isolation or benchmark quality.
