title: "Sandboxed Deployments"
description: "Deploy an agent into an OpenShell sandbox on Kubernetes and confirm it can reach the platform and nothing else."
---

A sandboxed deployment is a normal `nemo agents deploy --mode k8s`, with the platform's `k8s` executor pointed at an OpenShell gateway. The agent runs in a sandbox pod whose network policy allows one destination, the platform API. Model calls go through the platform's Inference Gateway as usual; a call to anywhere else is refused before it leaves the pod.

Nothing about the agent changes. The same image and the same config that would run as a plain Kubernetes Deployment run in the sandbox.

## Before you start

You need:

- A cluster with OpenShell installed and the platform's `openshell` executor configured, as described in [OpenShell](/documentation/kubernetes-deployment/setup/helm/openshell).
- The `nemo` CLI connected to that platform, with a model provider registered. If you have not done this yet, `nemo setup` walks you through it.
- Docker on your machine to build the agent image.
- The `openshell` CLI connected to the gateway, for the last step.

Set the names used below:

```sh
export NMP_NAMESPACE=nemo-platform
export NMP_HELM_RELEASE=nemo-platform
export AGENT_NAME=sandbox-hello
```

## Choose a model

List the models your platform serves and pick one for the agent:

```sh
nemo models list --all-pages
```

Use the id as printed, in the form `default/<name>`. Prefer an instruction-tuned chat model. A reasoning model can spend its whole token budget thinking and return an empty answer, which looks like a broken deployment when it is not.

Check that inference works before building anything, so a provider problem never gets mistaken for a sandbox problem:

```sh
curl -s -X POST "$NMP_BASE_URL/apis/inference-gateway/v2/workspaces/default/openai/-/v1/chat/completions" \
  -H 'content-type: application/json' \
  -d '{"model":"default/<name>","messages":[{"role":"user","content":"Say exactly: inference ok"}],"max_tokens":20}'
```

The response should contain `"content": "inference ok"`.

## Write the agent

Create a directory holding just the agent config. The directory is both the Docker build context and the bundle the platform stores, so keep it clean.

```sh
mkdir -p "agents/$AGENT_NAME"
cat > "agents/$AGENT_NAME/agent.yaml" <<EOF
config_format: nemo-agents-spec-v1
name: $AGENT_NAME
description: Small agent used to check an OpenShell sandbox deployment.

instructions:
  system:
    content: |
      You are a concise assistant running inside a NeMo Platform sandbox.
      Answer in one or two sentences. If asked where you run, say you are a
      sandboxed NeMo agent and that you cannot reach the public internet.

default_harness: deepagents

harnesses:
  deepagents:
    kind: deepagents
    settings:
      deepagents: {}

models:
  default:
    provider: nvidia
    model: default/<name>

skills:
  paths: []

mcp:
  servers: {}

tools:
  blocked: []

environment:
  workspace: ./workspace
EOF
```

Replace `default/<name>` with the model id from the previous step. The config needs no API key or `base_url`: the platform injects the Inference Gateway address when it deploys the agent.

## Build the image

Build with the OpenShell runtime profile, which adds the `sandbox` user the gateway runs the agent as:

```sh
nemo agents package \
  --agent "agents/$AGENT_NAME/agent.yaml" \
  --sandbox-runtime openshell \
  --tag "$AGENT_NAME:0.1"
```

The build takes a few minutes and produces an image of a few gigabytes. A long pause while the base image's default user is removed is normal.

Check the result:

```sh
docker run --rm --entrypoint sh "$AGENT_NAME:0.1" -c 'id sandbox; command -v curl'
```

You should see `uid=999(sandbox)` and `/usr/bin/curl`.

Get the image to the cluster. On a local cluster, load it directly:

```sh
k3d image import "$AGENT_NAME:0.1" -c <cluster>        # k3d
kind load docker-image "$AGENT_NAME:0.1" --name <cluster>   # kind
minikube image load "$AGENT_NAME:0.1"                  # minikube
```

On a remote cluster, rebuild with `--publish --registry <registry>` and use the pushed reference in the steps below. Keep a versioned tag rather than `latest`, so the node uses the loaded image instead of trying to pull.

## Register and deploy

Register the agent with the platform:

```sh
nemo agents create --name "$AGENT_NAME" --agent-config "agents/$AGENT_NAME/agent.yaml"
```

Deploy it. The `k8s` mode lands on the `openshell` executor because that is what the platform values name:

```sh
nemo agents deploy \
  --agent "$AGENT_NAME" \
  --name "$AGENT_NAME-sandbox" \
  --mode k8s \
  --image "$AGENT_NAME:0.1" \
  --timeout 600
```

The command reports `pending`, then `starting`, then `running`, usually within a minute, and ends with a line like:

```
Deployment 'sandbox-hello-sandbox' is running at http://default--nmp-d5936a3706f615--http.openshell.localhost:8080/
```

That URL is the gateway's internal name for the agent's service. It does not resolve from your machine, and you do not need it: the platform reaches the agent through the gateway for you.

While it comes up, you can watch the sandbox appear:

```sh
kubectl -n openshell get sandboxes.agents.x-k8s.io
kubectl -n openshell get pods -l managed-by=nemo-deployments
```

One Sandbox named `default--nmp-<hash>` with `READY` true, and its pod `Running`.

## Ask it something

```sh
nemo agents invoke --agent-deployment "$AGENT_NAME-sandbox" \
  --input "In one sentence, where are you running?"
```

The reply comes back in about ten seconds as a chat completion. The `content` should be a real sentence. If it is empty and you chose a reasoning model, switch to a chat model and redeploy.

## Confirm the sandbox is closed

The sandbox is named after the deployment. Get its name and run two commands inside it:

```sh
export SBX=$(openshell sandbox list | grep -o 'nmp-[0-9a-f]*' | head -1)

openshell sandbox exec --name "$SBX" -- curl -sS -m 5 https://example.com
openshell sandbox exec --name "$SBX" -- curl -sS -m 5 \
  "http://${NMP_HELM_RELEASE}-api.${NMP_NAMESPACE}.svc.cluster.local:8080/health/ready"
```

The first prints:

```
curl: (56) CONNECT tunnel failed, response 403
```

That is the sandbox proxy refusing a destination the policy does not list. The second prints `{"status":"ready"}`. Run the invoke once more and the agent still answers: the model call is the one route the policy allows.

## Clean up

```sh
nemo agents undeploy "$AGENT_NAME-sandbox" --yes
nemo agents delete "$AGENT_NAME" --yes
```

Undeploying removes the sandbox and its pod. The image stays in the cluster until you remove it.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `nemo agents deploy` returns 400: `deployment_mode 'k8s' resolved to executor 'openshell', which runs on 'openshell'` | Platform predates support for sandbox executors in `--mode k8s` | Upgrade the platform |
| Deployment `running` but `invoke` times out or returns 502 | Platform predates the gateway-routed proxy, or the agent process died | Upgrade the platform; if current, read the agent log: `openshell sandbox exec --name $SBX -- cat /tmp/nemo-serve.log` |
| Sandbox pod `ImagePullBackOff` | Image not loaded into the cluster, or a `latest` tag forcing a pull | Load or push the image; use a versioned tag |
| Sandbox pod crashes with `exec format error` | Image built for a different CPU architecture than the node | Rebuild with `--platform linux/amd64` or `linux/arm64` to match |
| Deployment `failed`: serve process exited, no log | Sandbox user cannot write to the working directory | Set `serve_workdir: /tmp` in the executor config |
| Agent log shows connection refused or name resolution errors to `<release>-api` | Agent was given the short Service name | Set `agents.deployments.k8s_internal_base_url` to the full `.svc.cluster.local` name and redeploy |
| Agent log shows the proxy denying the platform host | The binary making the call is not on the egress allow list | Compare `platform_egress.binaries` in the executor config with the interpreter path in the image (`/workspace/.venv/bin/python3.13` by default) |
| `example.com` reachable from inside the sandbox | You are in a different sandbox, or the deployment did not run on the `openshell` executor | Confirm `$SBX` is `nmp-<hash>` and check `nemo agents deployments get` |
| `nemo agents package` refuses a developmental version | `nemo` was installed from a source checkout | Install the released CLI, or build a wheel with `uv build --package nemo-platform --wheel` and set `NEMO_AGENTS_WHEEL` to it |

<Note>

`nemo agents deployments get` shows the config as it was when the deployment was created, including the platform's own view of its address. The config the agent actually received is the one inside the sandbox: `openshell sandbox exec --name $SBX -- cat /tmp/nemo/agent.yaml`.

</Note>
