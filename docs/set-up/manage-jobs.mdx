This section describes how to configure jobs in NeMo Helix. The Jobs service is responsible for scheduling batch jobs, collecting telemetry and managing job results.

## Listing Jobs by Type

Every plugin that submits jobs has a `list-jobs` command that lists only that plugin's jobs, newest first. Use `--type` to filter to specific job types; the command's help names them.

```bash
nemo data-designer list-jobs
nemo evals list-jobs --type agent-evaluate --filter.status completed
```

`nemo jobs list --type` does the same from the core jobs command. Pass a plugin to list all its job types, or `<plugin>.<job>` for one job type. Repeat `--type` to list several:

```bash
nemo jobs list --type evals
nemo jobs list --type evals.evaluate --type garak
```

When several job types are listed, the results are merged into one list. `--page-size` caps the merged list and `--all-pages` fetches every job; `--page` works only when exactly one job type is listed. Each job in the output has a `type` field naming its job type.

## Viewing Job Attempts

Each job run creates an attempt. The job response includes `attempt_id` for the current attempt. List the attempt history or retrieve the current attempt without first looking up its ID:

```bash
nemo jobs attempts list <job-name> --workspace default
nemo jobs attempts get current --job <job-name> --workspace default
```

Step and task APIs use attempt selectors to keep execution updates attached to the run that produced them. Log, watch, and tail commands also accept an attempt ID or `current` when you need data from a specific run.

Results remain job-owned, and result names are unique across the whole job. New result records include the concrete attempt ID that produced them. Use `nemo jobs results list <job-name> --attempt-id <attempt-id>` (or `--attempt-id current`) to filter the canonical result list. `nemo jobs results get` and `nemo jobs results download` identify a result directly by its job-wide unique name and do not need an attempt selector.

## Updating Jobs

Use `nemo jobs update` to change mutable metadata or the job definition used by future attempts:

```bash
nemo jobs update <job-name> \
  --workspace default \
  --description "Updated description"
```

Definition updates must provide both `spec` and `platform_spec`; the Jobs Factory recompiles plugin job specs before forwarding the paired fields. To clear a job description, use `--input-data '{"description": null}'`.

## Viewing Job Logs

Use `nemo jobs get-logs` to inspect paginated job logs:

```bash
nemo jobs get-logs <job-name> --workspace default --limit 100
```

Use `nemo jobs tail` when you only need the newest lines from a long or running job:

```bash
nemo jobs tail <job-name> --workspace default -n 500
```

Both commands support `--attempt-id`, `--step-id`, and `--task-id` to narrow the log output. The attempt selector accepts an attempt ID or `current`.

## Concurrency Limits and Queueing

The Jobs service bounds how much work runs at once. Before it starts a job step, the scheduler checks the number of jobs currently running against three limits. A step starts only when it is under all of them:

| Limit | Applies to | Default | Setting |
|---|---|---|---|
| Executor | Jobs running on one execution profile (`provider` and `profile`) | 8 for `docker` and `subprocess`, 500 for `kubernetes_job` and `volcano_job` | `max_active_jobs` in the execution profile `config` |
| Workspace | Jobs running in one workspace | 200 | `max_active_jobs_per_workspace` |
| User | Jobs running for one user | 50 | `max_active_jobs_per_user` |

```yaml
jobs:
  max_active_jobs_per_workspace: 200
  max_active_jobs_per_user: 50
  executors:
    - provider: gpu
      profile: a100-pool
      backend: kubernetes_job
      config:
        max_active_jobs: 20
```

On Kubernetes, the Helm chart sets these through `core.jobs.maxActiveJobsPerUser`, `core.jobs.maxActiveJobsPerWorkspace`, and `core.jobs.maxActiveJobs` (the executor limit for Kubernetes and Volcano profiles).

Each running job counts as one unit, no matter how many resources or tasks it uses. A job runs its steps one at a time, so the scheduler counts the job's current step: it counts toward the limits while it is `pending`, `active`, `cancelling`, or `pausing`. Queued, paused, and finished steps do not count. The scheduler counts current work each time it runs, so the limits do not depend on past usage.

### What happens at a limit

A step that does not fit is not failed. It moves to `queued`, and the reason, such as `executor cpu/default is at its limit (8/8 active jobs)`, appears in the step's `status_details.message`. The scheduler retries queued steps on every pass (every `schedule_interval_seconds`, 5 by default) and starts them as running jobs finish.

When many steps are waiting and capacity is limited, the scheduler takes one step per user in turn, so a user with a large backlog does not block other users. Each user's own steps still start in the order they were created.

If the scheduler cannot read the current load, it queues the steps for that pass and tries again on the next one.

<Note>

A per-workspace override is not available yet. Every workspace uses `max_active_jobs_per_workspace`. A limit per job group is also not available yet.

</Note>

## Execution Profiles

You can configure jobs to run on different hardware by specifying an execution profile. This allows you to define different compute resources and job execution backends for different job types and use cases.

An execution profile is defined by the following attributes:

- A profile name (`profile`)
- A compute provider (e.g. `cpu` or `gpu`)
- An [execution backend](#execution-backends) (e.g. `subprocess`, `docker`, `kubernetes_job`, `volcano_job`)

By default, NeMo Helix defines a default CPU and default GPU provider to launch CPU and GPU bound jobs.

You can configure multiple execution profiles to suit the shape of your compute environment. For example, if you have a compute environment with heterogeneous infrastructure (e.g., two types of GPU hardware such as A100 and H200), you can define a list of execution profiles as follows:

```yaml
jobs:
  executors:
    # Allow any CPU-bound job to run anywhere
    - provider: cpu
      profile: default
      backend: kubernetes_job
      config: {}

    # Run on A100 hardware
    - provider: gpu
      profile: a100-pool
      backend: kubernetes_job
      config:
        # Use the appropriate pod scheduling for a100-pool.
        node_selector:
          node-pool-name: a100-pool

    # Run on H200 hardware
    - provider: gpu
      profile: h200-pool
      backend: kubernetes_job
      config:
        # Use the appropriate pod scheduling for h200-pool.
        node_selector:
          node-pool-name: h200-pool
```

For full configuration details, see the [platform configuration reference](/documentation/kubernetes-deployment/config-reference).

### Default Execution Profiles

Each execution profile is addressed by its `(provider, profile)` pair. When a job does not request a named profile, it uses `profile: default` for its provider. The built-in profiles depend on the platform runtime.

- CPU provider: `provider: cpu`, `profile: default`.
- GPU provider: `provider: gpu`, `profile: default`.
- Local host subprocess provider: `provider: subprocess`, `profile: default`. It is enabled by default for Docker and no-control-plane runtimes, and disabled by default for Kubernetes.

You may configure the default execution profiles by updating the `executor_defaults` section of the `jobs` section of the [platform configuration](/documentation/kubernetes-deployment/config-reference). The structure of the `executor_defaults` matches the configuration of the execution backend configuration.

```yaml
jobs:
  executor_defaults:
    # Override the default Docker execution profile configuration.
    docker:
      storage:
        volume_name: nemo-jobs-storage

    # Override the default host subprocess execution profile configuration.
    subprocess:
      working_directory: /tmp/nhx-subprocess-jobs
      cleanup_completed_jobs_immediately: false

    # Override the default Kubernetes execution profile configuration.
    kubernetes_job:
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
      node_selector:
        kubernetes.io/arch: amd64

    # Override the default Volcano execution profile configuration.
    volcano_job:
      storage:
        pvc_name: nemo-jobs-storage
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
      node_selector:
        kubernetes.io/arch: amd64
```

## Execution Backends

Execution backends launch and manage job tasks. Docker, Kubernetes, and Volcano run tasks in containers; the subprocess backend runs a command directly on the control plane host.

NeMo Helix currently supports the following execution backends:

- Docker (`docker`)
- Kubernetes Jobs (`kubernetes_job`)
- Volcano Jobs (`volcano_job`)
- Subprocess (`subprocess`)

For when the **control plane** itself needs Docker (deployments preflight) versus when jobs use subprocess, see [Local Docker and Executors](/documentation/get-started/local-docker-and-executors). Inspect registered profiles with `nemo jobs list-execution-profiles -f json`.

### Subprocess

The subprocess backend runs job commands directly on the control plane host. It is useful for trusted local development workloads, but it does not provide container isolation and should not run untrusted code.

With `platform.runtime: docker` or `platform.runtime: none`, NeMo Helix registers `subprocess/default` unless it is explicitly disabled. Kubernetes deployments do not enable it by default. CPU container steps that request a configured subprocess profile are translated to this host backend only when `container.entrypoint` or `container.command` provides a command; otherwise job creation returns HTTP 422. Some local profiles (for example auditor and GPU/customizer) still use Docker even when `subprocess/default` is present.

```yaml
jobs:
  executors:
    - provider: subprocess
      profile: default
      backend: subprocess
      config:
        working_directory: /tmp/nhx-subprocess-jobs
        cleanup_completed_jobs_immediately: false
```

### Docker

NeMo Helix supports Docker as an execution backend for CPU and GPU based jobs. When the shared GPU pool is configured (see below), Docker will use only the configured GPU devices and will not over-schedule jobs if there are not currently enough GPUs available.

With `platform.runtime: docker`, NeMo Helix registers Docker-backed `cpu/default` and `gpu/default` profiles when Docker is available. Docker and `none` runtimes also register `subprocess/default` unless it is explicitly disabled; Kubernetes does not. CPU container steps that request a configured subprocess profile are translated to it only when `container.entrypoint` or `container.command` provides a command; otherwise job creation returns HTTP 422. Configure or select an explicit image-backed profile when a workload must run in a container. See [Local Docker and Executors](/documentation/get-started/local-docker-and-executors) for how this relates to control plane startup preflight (deployments) versus job backends.

<Tip>

If you are running GPU jobs with Docker, see [GPU Configuration](/documentation/get-started) for information on configuring the shared GPU pool. This configuration is shared between the jobs and models services to prevent GPU resource conflicts.

</Tip>

```yaml
jobs:
  executors:
    # Define the default CPU provider.
    - provider: cpu
      profile: default
      backend: docker
      config:
        storage:
          volume_name: nemo-helix_jobs_storage

    # Define the default GPU provider.
    - provider: gpu
      profile: default
      backend: docker
      config:
        storage:
          volume_name: nemo-helix_jobs_storage
```

### Kubernetes Jobs

NeMo Helix supports Kubernetes Jobs as an execution backend for CPU and GPU based jobs.

```yaml
jobs:
  executors:
    # Define the default CPU provider.
    - profile: default
      backend: kubernetes_job
      provider: cpu
      config:
        # Storage is the kubernetes_job storage configuration.
        storage:
          # Persistent volume claim used by launched jobs.
          pvc_name: nemo-core-jobs-storage

    # Define the default GPU provider.
    - profile: default
      backend: kubernetes_job
      provider: gpu
      config:
        storage:
          pvc_name: nemo-core-jobs-storage
        # Add integration metadata to Kubernetes Jobs and their pods.
        job_metadata:
          labels:
            my-custom-label: "value"
          annotations:
            example.com/annotation: "value"
        pod_metadata:
          labels:
            sidecar.istio.io/inject: "false"
          annotations:
            example.com/annotation: "value"
        # Configure standard Kubernetes pod scheduling behavior.
        node_selector:
          kubernetes.io/arch: amd64
        tolerations:
          - key: nvidia.com/gpu
            operator: Exists
            effect: NoSchedule
        affinity:
          nodeAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              nodeSelectorTerms:
                - matchExpressions:
                    - key: highmem
                      operator: In
                      values:
                        - "true"
```

#### KAI Scheduler

[KAI Scheduler](https://github.com/NVIDIA/KAI-Scheduler) is a Kubernetes scheduler for AI/ML workloads. You can direct Kubernetes Jobs to use KAI Scheduler by setting `scheduler_name` in the execution profile config, and by adding the required queue labels to the job and pod metadata.

```yaml
jobs:
  executors:
    - profile: default
      backend: kubernetes_job
      provider: gpu
      config:
        # Direct pods to the KAI scheduler.
        scheduler_name: kai-scheduler
        # Required labels for KAI Scheduler queue assignment.
        job_metadata:
          labels:
            kai.scheduler/queue-name: default
        pod_metadata:
          labels:
            kai.scheduler/queue-name: default
        storage:
          pvc_name: nemo-core-jobs-storage
```

See the [KAI Scheduler documentation](https://github.com/kai-scheduler/KAI-Scheduler/tree/main/docs) for more information on how to configure jobs with KAI Scheduler.

### Volcano Jobs

NeMo Helix supports Volcano Jobs as an execution backend for launching distributed GPU jobs. Install Volcano as a cluster engine; see [Volcano](/documentation/kubernetes-deployment/setup/helm/volcano).

Volcano Jobs are configured using the same configuration as Kubernetes Jobs, but with the following additional configuration:

- `queue`: The Volcano queue to submit the job to.
- `scheduler_name`: The Volcano scheduler to use for the job.
- `plugins`: The Volcano plugins to use for the job.
- `max_retry`: The maximum number of retries for the job.
- `enable_multi_node_networking`: Enable multi-node networking injection. Sets annotations to trigger Kyverno policy mutations. This is only available if the platform is configured to use multi-node networking (see [Multi-Node Networking](/documentation/kubernetes-deployment/setup/helm/multinode-networking)).

```yaml
jobs:
  executors:
    - profile: default
      backend: volcano_job
      provider: gpu_distributed
      config:
        queue: default
        scheduler_name: volcano
        plugins:
          pytorch: ["--master=leader", "--worker=worker", "--port=23456"]
        max_retry: 0
        # Add any other supported Kubernetes Job configuration here.
```
