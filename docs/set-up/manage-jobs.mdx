This section describes how to configure jobs in NeMo Helix. The Jobs service is responsible for scheduling batch jobs, collecting telemetry and managing job results.

## Creation and deletion lifecycle

A Job is visible as `creation_pending` while its resources are being prepared. It becomes `created` only after setup is durable. Execution and normal lifecycle mutations wait for that publication. A valid `created` Job can have no current Attempt; get, list, and status still return it, while attempt-dependent operations report that no Attempt exists.

Deletion first records `deletion_pending` on an eligible Job. HTTP 204 acknowledges that request; the Jobs controller finishes resource cleanup and removes the Job afterward. Poll the existing get operation using the returned Job ID until it returns not found when you need to wait for completion. A service error or timeout does not mean the Job has disappeared. Workspace deletion performs this wait before advancing to Files cleanup.

The controller retries failed cleanup and retains the Job until its known owned resources are settled. Caller-supplied output locations remain borrowed. Do not select another Job's auto-created artifact Fileset as an output location: that usage has no sharing protection. An unknown empty allocation can remain after an allocation response is lost, and can block a later create with the same name.

Deleting a legacy Job without an allocation receipt removes the Job and its child records but retains the unverified Fileset for reconciliation. That Fileset can still block creating another Job with the same name until it is reconciled.

`jobs.storage.creation_timeout_seconds` sets the grace before unfinished creation becomes eligible for automatic cleanup; its default is 900 seconds. Accepted deletion is eligible for cleanup immediately, including for recently created Jobs. An explicit deletion request can also end unfinished creation before this timeout. Run exactly one active Jobs cleanup controller. The supplied Helm deployment uses one replica and a Recreate rollout; custom startup, restart, and failover procedures must stop the old controller before starting its replacement.

Continuing SDK handles and watches retain the Job ID they received, so ordinary deletion and recreation under the same name does not move them to the replacement. Existing HTTP addressing still tries an ID and then a name. A literal Job name equal to a disappeared ID remains ambiguous at that public boundary.

## Listing Jobs by Type

Every plugin that submits jobs has a `list-jobs` command that lists only that plugin's jobs, newest first. Use `--type` to filter to specific job types; the command's help names them.

```bash
nemo data-designer list-jobs
nemo evals list-jobs --type agent-evaluate --filter.status completed
```

`nemo jobs list --type` does the same from the core jobs command. Pass a plugin to list all its job types, or `<plugin>.<job>` for one job type. Repeat `--type` to list several:

```bash
nemo jobs list --type evals
nemo jobs list --type evals.evaluate --type garak
```

When several job types are listed, the results are merged into one list. `--page-size` caps the merged list and `--all-pages` fetches every job; `--page` works only when exactly one job type is listed. Each job in the output has a `type` field naming its job type.

## Viewing Job Attempts

Each job run creates an attempt. The job response includes `attempt_id` for the current attempt. List the attempt history or retrieve the current attempt without first looking up its ID:

```bash
nemo jobs attempts list <job-name> --workspace default
nemo jobs attempts get current --job <job-name> --workspace default
```

Step and task APIs use attempt selectors to keep execution updates attached to the run that produced them. Log, watch, and tail commands also accept an attempt ID or `current` when you need data from a specific run.

Results remain job-owned, and result names are unique across the whole job. New result records include the concrete attempt ID that produced them. Use `nemo jobs results list <job-name> --attempt-id <attempt-id>` (or `--attempt-id current`) to filter the canonical result list. `nemo jobs results get` and `nemo jobs results download` identify a result directly by its job-wide unique name and do not need an attempt selector.

## Updating Jobs

Use `nemo jobs update` to change mutable metadata or the job definition used by future attempts:

```bash
nemo jobs update <job-name> \
  --workspace default \
  --description "Updated description"
```

Definition updates must provide both `spec` and `platform_spec`; the Jobs Factory recompiles plugin job specs before forwarding the paired fields. To clear a job description, use `--input-data '{"description": null}'`.

## DAG workflows (prototype)

Opt a platform job into DAG scheduling with `platform_spec.workflow`. Set its
`mode` to `run_to_completion` (the default) or `continuous`. Every workflow step
must declare `depends_on`, including an empty list for roots. Optional `inputs`
contains objects with a `fileset_id`. Job create and update reject cycles,
unknown dependencies, duplicate input references, and workflow-only fields on
sequential jobs.

The controller compares each node's input Filesets' opaque `commit_revision`
values. Uploading files alone does not request another execution: explicitly
commit the Fileset after updating its inputs. Outputs do not affect scheduling.
Dependencies order execution; each node's own inputs determine whether it needs
to run again. The controller evaluates dependencies from roots to leaves. A
blocked node cannot release its children using an earlier success. Once its
ancestors recover, its unchanged inputs can reuse that success.

An Attempt keeps the definition and original execution context it started with.
Editing the Job takes effect in a new Attempt through the existing start/rerun
operation. Terminal Attempts stay terminal. Sequential jobs retain their current
behavior when `workflow` is omitted.

A current workflow can wait without creating any Steps. If a rerun Attempt is
saved but never becomes current, the controller marks it `ERROR` after the
existing creation timeout. This recovery preserves the current Attempt and
shared storage, and allows Job deletion to proceed.

A continuous Attempt stays active when its nodes are clean, failed or cancelled.
Unchanged failed or cancelled inputs wait for an input commit or manual
invalidation; backend retries are unchanged. Cancelling a node cancels its
dependent branch while independent runnable branches finish the pass. A
run-to-completion Attempt then ends `CANCELLED`; a continuous Attempt stays open
and can retry cancelled nodes in a later pass. Cancelling the whole workflow
ends its Attempt `CANCELLED` in either mode. Once workflow cancellation has been
accepted, pause returns `409 Conflict` and cancellation continues. Step errors
reported during cancellation retain their diagnostics while the Attempt still
finishes `CANCELLED`. Internal cleanup of unstarted executions does not turn a
workflow failure into a user cancellation.

To invalidate selected nodes, PATCH the existing
`/apis/jobs/v2/workspaces/{workspace}/jobs/{job}/attempts/{attempt}/status-details`
route with this body:

```json
{
  "workflow_invalidation": {
    "request_id": "manual-run-1",
    "steps": ["prepare", "evaluate"]
  }
}
```

`trigger` lists events with OR semantics. A new commit from any listed Fileset
or a new successful execution of any listed Step requests a run. `depends_on`
lists readiness conditions with AND semantics: every Fileset must have a commit
and every referenced Step must have a successful execution. Earlier successful
executions remain sufficient for typed readiness conditions.

```yaml
name: evaluate
depends_on:
  - step_success: prepare
  - fileset_commit: <configuration-fileset-id>
trigger:
  - fileset_commit: <input-fileset-id>
  - step_success: refresh
# executor: ...
```

Here, either an input commit or a successful `refresh` requests `evaluate`.
It waits for a successful `prepare` and a committed configuration Fileset.
Configuration commits alone do not request another run.

An existing Fileset commit counts as an initial trigger. A Step trigger waits for
its first successful execution. Without event inputs or triggers, a node runs
once when ready. Later passes preserve consumed commits and success execution
IDs, so old events do not fire again. Multiple events before execution coalesce.
Events remain pending while prerequisites are unavailable. Each node runs at most
once per pass; later events wait for the next pass. Step successes produced in a
pass can trigger downstream nodes that have not run in that pass.

Existing `inputs` remain Fileset change inputs. Existing string dependencies
such as `depends_on: [prepare]` retain their dependency/reuse behavior. Both
trigger and dependency Step references participate in cycle validation on
create/update. Fileset references are checked for access before persistence.

Use another request ID for another invalidation. Repeating the current signal
for a node does not request extra work. Invalidations can remain pending while
paused and cannot bypass failed dependencies. Input changes and invalidations
received during a pass coalesce into a later pass after the current pass drains.
Each pass resets the nodes' per-pass completion, scheduling and blocker state,
then captures every node's input revisions and run decision. Successful input
baselines and execution history remain available, so clean nodes can be reused.
New events do not replace queued executions or change downstream decisions in
that pass.
The same logical node never has overlapping executions. These recorded revisions
track changes; they do not freeze the contents of a Fileset.

Pause is Attempt-level: it stops further admission, drains already-admitted work
and holds the remaining nodes. An admitted execution can still be waiting for
backend capacity; it remains part of the drain. The Attempt reaches `PAUSED`
when admitted work finishes. Resume continues the same pass of the same Attempt. Existing storage-retention TTLs and expiry actions apply; a
workflow pause uses the time the Attempt reached paused, even when no individual
Step is paused. A failed node does not expire shared storage while a continuous
Attempt remains active.

The status API and `jobs watch` expose each logical node's freshness
(`unknown`, `dirty`, or `clean`), scheduling state (including `admitted` before
backend launch), blockers, requested revision,
execution IDs, latest outcome and input-observation timestamps/errors. The
controller alone writes `workflow_state`; ordinary progress details are separate.
Each node keeps its active execution ID, current-pass revision/input snapshot,
execution snapshot and latest input observations there; Step records contain ordinary execution status, Tasks and logs.
Status reads do not poll inputs or schedule work. Use `attempt_id` on status
reads or `--attempt-id` on watch to select an Attempt. The sync and async typed
clients accept `get_job_status(..., attempt_id=...)`. Execution history remains
available through the existing paginated Attempt step routes. Results keep their
existing Job-wide names and overwrite behavior.

## Viewing Job Logs

Use `nemo jobs get-logs` to inspect paginated job logs:

```bash
nemo jobs get-logs <job-name> --workspace default --limit 100
```

Use `nemo jobs tail` when you only need the newest lines from a long or running job:

```bash
nemo jobs tail <job-name> --workspace default -n 500
```

Both commands support `--attempt-id`, `--step-id`, and `--task-id` to narrow the log output. The attempt selector accepts an attempt ID or `current`.

## Concurrency Limits and Queueing

The Jobs service bounds how much work runs at once. Before it starts a job step, the scheduler checks the number of jobs currently running against three limits. A step starts only when it is under all of them:

| Limit | Applies to | Default | Setting |
|---|---|---|---|
| Executor | Jobs running on one execution profile (`provider` and `profile`) | 8 for `docker` and `subprocess`, 500 for `kubernetes_job` and `volcano_job` | `max_active_jobs` in the execution profile `config` |
| Workspace | Jobs running in one workspace | 200 | `max_active_jobs_per_workspace` |
| User | Jobs running for one user | 50 | `max_active_jobs_per_user` |

```yaml
jobs:
  max_active_jobs_per_workspace: 200
  max_active_jobs_per_user: 50
  executors:
    - provider: gpu
      profile: a100-pool
      backend: kubernetes_job
      config:
        max_active_jobs: 20
```

On Kubernetes, the Helm chart sets these through `core.jobs.maxActiveJobsPerUser`, `core.jobs.maxActiveJobsPerWorkspace`, and `core.jobs.maxActiveJobs` (the executor limit for Kubernetes and Volcano profiles).

Each running job counts as one unit, no matter how many resources or tasks it uses. A job runs its steps one at a time, so the scheduler counts the job's current step: it counts toward the limits while it is `pending`, `active`, `cancelling`, or `pausing`. Queued, paused, and finished steps do not count. The scheduler counts current work each time it runs, so the limits do not depend on past usage.

### What happens at a limit

A step that does not fit is not failed. It moves to `queued`, and the reason, such as `executor cpu/default is at its limit (8/8 active jobs)`, appears in the step's `status_details.message`. The scheduler retries queued steps on every pass (every `schedule_interval_seconds`, 5 by default) and starts them as running jobs finish.

When many steps are waiting and capacity is limited, the scheduler takes one step per user in turn, so a user with a large backlog does not block other users. Each user's own steps still start in the order they were created.

If the scheduler cannot read the current load, it queues the steps for that pass and tries again on the next one.

<Note>

A per-workspace override is not available yet. Every workspace uses `max_active_jobs_per_workspace`. A limit per job group is also not available yet.

</Note>

## Pulling inputs and publishing Task output

Set `filesets` on a platform Step to copy Fileset contents into each Task before
its script runs and upload directories after the Step's workload finishes:

```yaml
platform_spec:
  steps:
    - name: transform
      executor:
        provider: cpu
        container:
          image: busybox:stable
          command:
            - sh
            - -c
            - mkdir -p /work/output /work/diagnostics; cp /work/input/data.txt /work/output/result.txt
      filesets:
        pull:
          - fileset_id: fileset-input-id
            directory: /work/input
        push:
          - fileset_id: fileset-output-id
            directory: /work/output
            path: results
            when: success
          - fileset_id: fileset-diagnostics-id
            directory: /work/diagnostics
            when: always
```

Use immutable IDs for existing Filesets in the Job's workspace. Choose directories
that are writable and accessible in the selected execution profile. `path` is a
relative prefix inside the Fileset and defaults to its root. The example produces
`results/result.txt`; it does not add the local directory name or a Task ID.

Each parallel Task uploads its own configured directories. Tasks may use private
scratch or separate RWO volumes; publishing their output does not require one
filesystem shared across nodes. Explicit shared workload mounts still follow
their storage driver's access and scheduling rules. The local subprocess profile
needs `launcher_tool_path` pointing to an executable host `jobs-launcher`.

| `when` | Publication condition |
| --- | --- |
| `always` (default) | Successful or failed aggregate Step workload |
| `success` | Successful aggregate Step workload |
| `failure` | Failed aggregate Step workload |

The controller waits for required pulls before starting the workload. Pull failure
fails the Step. After its workload processes stop, the Step supplies the same
aggregate outcome to its uploaders. Required uploads finish before the controller
explicitly commits each destination and finalizes the Step. A successful script
with failed publication makes the Step fail; diagnostic publication cannot turn
a failed script into success. Cancellation stops normal publication, and pause
does not count as workload completion.

Transfers preserve relative filenames and overwrite matching files. The Step/Task
author owns filename collisions and coordination between concurrent writers. The
platform adds no prefixes, conflict checks or cross-writer locks, and it does not
delete destination-only files. Directory entries run in declaration order within
a Task; Tasks can upload concurrently. Symlinks and paths escaping a selected
directory are rejected. A missing local upload directory fails that publication;
an existing empty directory succeeds.

Transient transfer/commit failures receive up to three attempts. A surviving Task
retries from its existing directories. Node loss can destroy Task-local output,
so another Task cannot recover it without retained storage. An uncertain commit
response may cause a repeated commit and another downstream notification. Commits
are change markers, not snapshots or transactions across concurrent writers.
The current phase and commit results appear in Step status details under
`fileset_transfers`.

## Execution Profiles

You can configure jobs to run on different hardware by specifying an execution profile. This allows you to define different compute resources and job execution backends for different job types and use cases.

An execution profile is defined by the following attributes:

- A profile name (`profile`)
- A compute provider (e.g. `cpu` or `gpu`)
- An [execution backend](#execution-backends) (e.g. `subprocess`, `docker`, `kubernetes_job`, `volcano_job`)

By default, NeMo Helix defines a default CPU and default GPU provider to launch CPU and GPU bound jobs.

You can configure multiple execution profiles to suit the shape of your compute environment. For example, if you have a compute environment with heterogeneous infrastructure (e.g., two types of GPU hardware such as A100 and H200), you can define a list of execution profiles as follows:

```yaml
jobs:
  executors:
    # Allow any CPU-bound job to run anywhere
    - provider: cpu
      profile: default
      backend: kubernetes_job
      config: {}

    # Run on A100 hardware
    - provider: gpu
      profile: a100-pool
      backend: kubernetes_job
      config:
        # Use the appropriate pod scheduling for a100-pool.
        node_selector:
          node-pool-name: a100-pool

    # Run on H200 hardware
    - provider: gpu
      profile: h200-pool
      backend: kubernetes_job
      config:
        # Use the appropriate pod scheduling for h200-pool.
        node_selector:
          node-pool-name: h200-pool
```

For full configuration details, see the [platform configuration reference](/documentation/kubernetes-deployment/config-reference).

### Default Execution Profiles

Each execution profile is addressed by its `(provider, profile)` pair. When a job does not request a named profile, it uses `profile: default` for its provider. The built-in profiles depend on the platform runtime.

- CPU provider: `provider: cpu`, `profile: default`.
- GPU provider: `provider: gpu`, `profile: default`.
- Local host subprocess provider: `provider: subprocess`, `profile: default`. It is enabled by default for Docker and no-control-plane runtimes, and disabled by default for Kubernetes.

You may configure the default execution profiles by updating the `executor_defaults` section of the `jobs` section of the [platform configuration](/documentation/kubernetes-deployment/config-reference). The structure of the `executor_defaults` matches the configuration of the execution backend configuration.

```yaml
jobs:
  executor_defaults:
    # Override the default Docker execution profile configuration.
    docker:
      storage:
        volume_name: nemo-jobs-storage

    # Override the default host subprocess execution profile configuration.
    subprocess:
      working_directory: /tmp/nhx-subprocess-jobs
      cleanup_completed_jobs_immediately: false

    # Override the default Kubernetes execution profile configuration.
    kubernetes_job:
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
      node_selector:
        kubernetes.io/arch: amd64

    # Override the default Volcano execution profile configuration.
    volcano_job:
      storage:
        pvc_name: nemo-jobs-storage
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
      node_selector:
        kubernetes.io/arch: amd64
```

## Execution Backends

Execution backends launch and manage job tasks. Docker, Kubernetes, and Volcano run tasks in containers; the subprocess backend runs a command directly on the control plane host.

NeMo Helix currently supports the following execution backends:

- Docker (`docker`)
- Kubernetes Jobs (`kubernetes_job`)
- Volcano Jobs (`volcano_job`)
- Subprocess (`subprocess`)

For when the **control plane** itself needs Docker (deployments preflight) versus when jobs use subprocess, see [Local Docker and Executors](/documentation/get-started/local-docker-and-executors). Inspect registered profiles with `nemo jobs list-execution-profiles -f json`.

### Subprocess

The subprocess backend runs job commands directly on the control plane host. It is useful for trusted local development workloads, but it does not provide container isolation and should not run untrusted code.

With `platform.runtime: docker` or `platform.runtime: none`, NeMo Helix registers `subprocess/default` unless it is explicitly disabled. Kubernetes deployments do not enable it by default. CPU container steps that request a configured subprocess profile are translated to this host backend only when `container.entrypoint` or `container.command` provides a command; otherwise job creation returns HTTP 422. Some local profiles (for example auditor and GPU/customizer) still use Docker even when `subprocess/default` is present.

```yaml
jobs:
  executors:
    - provider: subprocess
      profile: default
      backend: subprocess
      config:
        working_directory: /tmp/nhx-subprocess-jobs
        cleanup_completed_jobs_immediately: false
```

### Docker

NeMo Helix supports Docker as an execution backend for CPU and GPU based jobs. When the shared GPU pool is configured (see below), Docker will use only the configured GPU devices and will not over-schedule jobs if there are not currently enough GPUs available.

With `platform.runtime: docker`, NeMo Helix registers Docker-backed `cpu/default` and `gpu/default` profiles when Docker is available. Docker and `none` runtimes also register `subprocess/default` unless it is explicitly disabled; Kubernetes does not. CPU container steps that request a configured subprocess profile are translated to it only when `container.entrypoint` or `container.command` provides a command; otherwise job creation returns HTTP 422. Configure or select an explicit image-backed profile when a workload must run in a container. See [Local Docker and Executors](/documentation/get-started/local-docker-and-executors) for how this relates to control plane startup preflight (deployments) versus job backends.

<Tip>

If you are running GPU jobs with Docker, see [GPU Configuration](/documentation/get-started) for information on configuring the shared GPU pool. This configuration is shared between the jobs and models services to prevent GPU resource conflicts.

</Tip>

```yaml
jobs:
  executors:
    # Define the default CPU provider.
    - provider: cpu
      profile: default
      backend: docker
      config:
        storage:
          volume_name: nemo-helix_jobs_storage

    # Define the default GPU provider.
    - provider: gpu
      profile: default
      backend: docker
      config:
        storage:
          volume_name: nemo-helix_jobs_storage
```

### Kubernetes Jobs

NeMo Helix supports Kubernetes Jobs as an execution backend for CPU and GPU based jobs.

```yaml
jobs:
  executors:
    # Define the default CPU provider.
    - profile: default
      backend: kubernetes_job
      provider: cpu
      config:
        # Storage is the kubernetes_job storage configuration.
        storage:
          # Persistent volume claim used by launched jobs.
          pvc_name: nemo-core-jobs-storage

    # Define the default GPU provider.
    - profile: default
      backend: kubernetes_job
      provider: gpu
      config:
        storage:
          pvc_name: nemo-core-jobs-storage
        # Add integration metadata to Kubernetes Jobs and their pods.
        job_metadata:
          labels:
            my-custom-label: "value"
          annotations:
            example.com/annotation: "value"
        pod_metadata:
          labels:
            sidecar.istio.io/inject: "false"
          annotations:
            example.com/annotation: "value"
        # Configure standard Kubernetes pod scheduling behavior.
        node_selector:
          kubernetes.io/arch: amd64
        tolerations:
          - key: nvidia.com/gpu
            operator: Exists
            effect: NoSchedule
        affinity:
          nodeAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              nodeSelectorTerms:
                - matchExpressions:
                    - key: highmem
                      operator: In
                      values:
                        - "true"
```

#### KAI Scheduler

[KAI Scheduler](https://github.com/NVIDIA/KAI-Scheduler) is a Kubernetes scheduler for AI/ML workloads. You can direct Kubernetes Jobs to use KAI Scheduler by setting `scheduler_name` in the execution profile config, and by adding the required queue labels to the job and pod metadata.

```yaml
jobs:
  executors:
    - profile: default
      backend: kubernetes_job
      provider: gpu
      config:
        # Direct pods to the KAI scheduler.
        scheduler_name: kai-scheduler
        # Required labels for KAI Scheduler queue assignment.
        job_metadata:
          labels:
            kai.scheduler/queue-name: default
        pod_metadata:
          labels:
            kai.scheduler/queue-name: default
        storage:
          pvc_name: nemo-core-jobs-storage
```

See the [KAI Scheduler documentation](https://github.com/kai-scheduler/KAI-Scheduler/tree/main/docs) for more information on how to configure jobs with KAI Scheduler.

### Volcano Jobs

NeMo Helix supports Volcano Jobs as an execution backend for launching distributed GPU jobs. Install Volcano as a cluster engine; see [Volcano](/documentation/kubernetes-deployment/setup/helm/volcano).

Volcano Jobs are configured using the same configuration as Kubernetes Jobs, but with the following additional configuration:

- `queue`: The Volcano queue to submit the job to.
- `scheduler_name`: The Volcano scheduler to use for the job.
- `plugins`: The Volcano plugins to use for the job.
- `max_retry`: The maximum number of retries for the job.
- `enable_multi_node_networking`: Enable multi-node networking injection. Sets annotations to trigger Kyverno policy mutations. This is only available if the platform is configured to use multi-node networking (see [Multi-Node Networking](/documentation/kubernetes-deployment/setup/helm/multinode-networking)).

```yaml
jobs:
  executors:
    - profile: default
      backend: volcano_job
      provider: gpu_distributed
      config:
        queue: default
        scheduler_name: volcano
        plugins:
          pytorch: ["--master=leader", "--worker=worker", "--port=23456"]
        max_retry: 0
        # Add any other supported Kubernetes Job configuration here.
```
