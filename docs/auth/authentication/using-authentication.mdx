How to log in, make authenticated API calls, manage tokens, and create Scoped Access Keys with the CLI and SDK.

**Prerequisites**: For OIDC login, configure an identity provider first. See [OIDC](/documentation/access-control/authentication/oidc-setup). For local testing without OIDC, use `nemo auth login --unsigned-token --email <email>`. Scoped Access Keys also require the administrator to enable `auth.access_keys.enabled`; see [Authentication Configuration](/documentation/access-control/deployment#scoped-access-keys).

## Log In

The device flow is the recommended login method. It opens your browser to authenticate with your organization's identity provider.

```bash
nemo auth login
```

Expected output:

```text
To sign in, use a web browser to open the page https://microsoft.com/devicelogin
and enter the code ABCD-EFGH to authenticate.
Waiting for authentication...
```

Open the URL, enter the code, and sign in with your IdP credentials. After consent, verify:

```bash
nemo auth status
```

```text
Authentication Status
Cluster             https://nhx.company.com
Context             default
Config File         /home/alice/.config/nhx/config.yaml
Auth Type           oauth
Credential Source   config file
Email               alice@company.com
Scopes              platform:read platform:write
Expires             2026-02-15T14:30:00+00:00 (1h 0m remaining)
Refresh Token       available (run 'nemo auth refresh' to renew)
Token               eyJhbGciOiJSUzI1NiIs...abc1234567
```

All CLI and SDK commands now use the stored token automatically.

### Requesting Specific Scopes

By default, the CLI requests the OAuth scopes returned by auth discovery in `default_scopes`. Deployments commonly include OIDC protocol scopes such as `openid`, `profile`, `email`, and `offline_access`, and may also include NeMo Helix API scope names such as `platform:read` and `platform:write`.

The CLI sends API scopes in the form required by the configured OAuth application. If auth discovery includes a resource scope prefix, the login output shows both the short name and the fully qualified value:

```text
Requesting scopes:
  platform:read (api://<app-client-id>/platform:read)
  platform:write (api://<app-client-id>/platform:write)
  openid
  profile
  email
  offline_access
```

Pass `--scope` to override the NeMo Helix API scopes requested for one login. The CLI keeps the non-API OIDC defaults and applies the discovered prefix automatically:

```bash
nemo auth login --scope "platform:read"
```

OAuth scopes requested during login are not group claims and do not grant workspace roles. Workspace authorization still comes from NeMo Helix role bindings over the configured identity claims. If the IdP returns recognized NeMo Helix API scopes in `scp` or `scope`, those scopes narrow the API calls that token can make. See [API Scopes](/documentation/access-control/authorization/api-scopes) for the authorization-scope model.

### Non-Interactive Login (CI/CD)

For CI pipelines, use the password grant to obtain a token without a browser: `nemo auth login --username <user> --password <pass>` (or set `NHX_OIDC_USERNAME` / `NHX_OIDC_PASSWORD` environment variables). If your CI system can obtain tokens directly (e.g., workload identity federation), pass the token via `auth` as shown in [Make API Calls](#make-api-calls) below.

<Warning>

Password grant sends credentials directly to the IdP and **bypasses MFA**. Many production IdPs disable it. Use a dedicated IdP automation identity with minimal scopes where possible.

</Warning>
## Make API Calls

### Python SDK

The SDK reads credentials from the CLI config automatically — no manual token handling needed:

```python
from nemo_helix_plugin.client.client import NemoClient

# After `nemo auth login` (OIDC) or `nemo auth login --unsigned-token --email <email>` (quickstart),
# from_config reads base_url, workspace, and the stored token from the CLI config.
# This is the recommended pattern for interactive / OIDC-authenticated usage.
client = NemoClient.from_config()

for workspace in client.workspaces.list_workspaces().items():
    print(workspace.name)
```

In CI jobs or containers without a CLI configuration file, set `NHX_BASE_URL` and `NHX_ACCESS_TOKEN` instead; `from_config()` reads them. For more about CLI contexts and these overrides, see [Connect with CLI Contexts](/documentation/reference/cli-reference/connect-to-deployments).

If you need explicit token control (for example, a token your CI system issues at runtime), construct the client directly and pass the token via `auth`:

```python
from nemo_helix_plugin.client.client import NemoClient

token = "<access-token>"  # for example, read from your CI system's secret store
client = NemoClient(
    base_url="https://nhx.company.com",
    workspace="default",
    auth=token,
)
```

### HTTP (curl)

```bash
TOKEN=$(nemo auth token)
curl -H "Authorization: Bearer $TOKEN" \
 https://nhx.company.com/apis/entities/v2/workspaces
```

## Scoped Access Keys for Non-SDK Clients

When Scoped Access Keys are enabled, a signed-in user can create a bearer token
for automation that cannot use the SDK's OIDC refresh flow:

```bash
# Create a Scoped Access Key with the platform default expiry and print the token once.
nemo auth access-keys create --name ci-build --description "CI build automation"
```

Scoped Access Key management commands live under the `auth` namespace as
`nemo auth access-keys ...`. The `access-keys` command group is not a top-level CLI
command and is not a separate NeMo Helix plugin.

By default, `create` makes a user-bound key for the signed-in user's effective
principal. A human HelixAdmin can instead create a service-account-bound key:

```bash
nemo auth access-keys create \
  --service-account intake-otel-writer \
  --name intake-otel-write \
  --expires-in 604800
```

The service account does not need to exist in the IdP and does not run
`nemo auth login`. NeMo stamps the token subject as
`service-account:intake-otel-writer`; grant workspace access to that prefixed
principal with `nemo workspaces members ...`.

<Note>

The access-key create CLI supports `--service-account`, `--expires-in`,
`--scope`, and `--workspace`. Use `--scope` to restrict the key to service
areas, and use workspace role bindings or `--workspace` to constrain which
workspaces that service-account principal can access. API-scope checks also
apply to bearer tokens that contain `scope` or `scp` claims, such as OIDC access
tokens.

</Note>

`create` prints the Scoped Access Key token once. Store it in your secret
manager and send it in the standard `Authorization` header:

```bash
curl -H "Authorization: Bearer $NHX_SCOPED_ACCESS_KEY" \
 https://nhx.company.com/apis/entities/v2/workspaces
```

Scoped Access Keys are signed JWT bearer tokens scoped to a principal identity.
User-bound keys preserve the user's principal and groups at creation time.
Service-account-bound keys use a non-human `service-account:<id>` principal and
do not carry user email or group claims. By default, new keys use the platform's
configured default expiry, which is 30 days unless the administrator changes it.
Pass `--expires-in <seconds>` to request a specific finite lifetime. Pass
`--expires-in none` only for deployments where the administrator has explicitly
allowed unlimited keys.

Restrict a key to specific services with `--scope`, and grant its principal
workspace membership with `--workspace` (formatted `<workspace>` or
`<workspace>:<role1>,<role2>`, repeatable; the role defaults to `Editor`) instead
of a separate `nemo workspaces members create` call. Without `--service-account`,
the key is a personal, user-bound key:

```bash
nemo auth access-keys create --name "intake-worker" \
  --scope intake,entities --workspace ml-team:Editor
```

Pass `--service-account <id>` to create a service-bound key that authenticates as
that service account instead, as described below.

#### Service-bound keys and workspaces

A key created with `--service-account` authenticates as that service account
rather than as you. With `--workspace`, the service account gets the roles you
name in each workspace. If the account is named `<workspace>--<name>` after one
of those workspaces, the key is also **bound** to each of them, so their Admins
can manage it. A workspace Admin can create such a key; a HelixAdmin can create
one for any service account.

Bind a key to one workspace:

```bash
nemo auth access-keys create --name otel \
  --service-account team-a--otel-collector \
  --workspace team-a:Editor
```

Bind it to several by repeating the option. The service account gets the role
you name in each workspace:

```bash
nemo auth access-keys create --name shared-ci \
  --service-account team-a--shared-ci \
  --workspace team-a:Editor \
  --workspace team-b:Viewer
```

Without `--workspace`, or for an account whose name isn't `<workspace>--<name>`
after one of the `--workspace` workspaces, the key isn't bound to any workspace
and only a HelixAdmin can create and manage it. Use this for platform-owned
accounts that workspace Admins shouldn't manage: the account still gets the roles
named with `--workspace`. You can also grant them separately with
`nemo workspaces members create --principal service-account:<id>`. Granting roles
that way never asks for confirmation, even if the account already has keys bound
to other workspaces; see the warning under
[Confirming access for existing workspace-bound keys](#confirming-access-for-existing-workspace-bound-keys).

A key bound to several workspaces is managed by someone who is an Admin of
**all** of them (or by a HelixAdmin). An Admin of only `team-a` can't create it
(`403`), and `list` leaves it out.

If they try to suspend, unsuspend, rotate, or revoke it, the key is left unchanged
and the request fails with `403` and the code `bound_workspaces_not_administered`.
The CLI shows this as a warning naming the bound workspaces they aren't an Admin
of. Workspaces they can't see, or that no longer exist, are only counted:

```text
Warning: Scoped Access Key ak_... is also bound to workspace(s) 'team-b', which you aren't Admin of; only a HelixAdmin, or an Admin of every workspace it's bound to, can revoke it
Error: Scoped Access Key ak_... was not revoked.
```

Someone who isn't an Admin of any of the key's workspaces gets `404`, as if the key
didn't exist.

Creating these keys with a `--scope`-restricted key needs `entities` or `platform`
in its scope, so the platform can read the workspaces; otherwise the request fails
with `400` and says so. A workspace Admin managing existing keys needs that scope
too: without it, the keys bound to their workspaces read as not found (`404`).

What each caller can do with a service-bound key:

| Caller | Create | Suspend, unsuspend, revoke | Rotate |
| --- | --- | --- | --- |
| HelixAdmin | Any service account | Any key | Any key |
| Admin of every bound workspace | A `<workspace>--<name>` account with no access outside the bound workspaces | Suspend and revoke: yes. Unsuspend: only while the account still has no access outside the bound workspaces | Any key whose account still has no access outside the bound workspaces |
| Admin of only some of the bound workspaces, or none | No | No | No |

`list` shows the service-bound keys bound to workspaces you administer, whoever
created them, so every Admin of a workspace sees its keys. Callers who aren't an
Admin of any workspace only see their personal keys. Bound workspaces are shown by
their current name. If the platform can't check a workspace's Admin role
while listing, the service-bound keys bound to that workspace are left out until a
retry.

##### Service account names

A workspace Admin must name the service account after one of the bound workspaces,
as `<workspace>--<name>`, for example `team-a--otel-collector`. A key bound to `team-a`
and `team-b` can use `team-a--...` or `team-b--...`. Any other name is rejected with
`403`. Workspace names can't contain `--`, so the prefix always names exactly one
workspace. The name also keeps the account under its workspace's control: only a
HelixAdmin or an Admin of `team-a` can grant `service-account:team-a--...` a role in
another workspace, for example with `nemo workspaces members create`. The account
itself still becomes Admin of any workspace it creates, if it's allowed to create
workspaces. That is access outside its bound workspaces, so its workspace's Admins
can then no longer rotate or unsuspend its keys (see below) until a HelixAdmin
removes it.

Service account names can't contain `@`, so the Admins of a workspace whose name
contains `@` can't create service-bound keys; a HelixAdmin has to create them. Avoid
`/` in service account names: `nemo workspaces members update` and `delete` can't
address an account whose name contains one.

Service account names are shared across the platform, and roles belong to the
account. The prefix stops a workspace's Admins from claiming a generic name, such as
`otel-collector`, that someone else later grants access elsewhere: their key would
silently get that access too. A HelixAdmin's key follows the same naming: it is
bound, and so handed to the bound workspaces' Admins, only for an account named
after one of its workspaces. Those Admins can then suspend, revoke, and rotate it,
subject to the restrictions below.

<Warning>
Names of the form `<workspace>--<name>` belong to the Admins of `<workspace>`, even
before that workspace exists: anyone who creates a workspace with that name can
create keys for its `<workspace>--...` accounts, as long as the account has no
access outside it. Until the workspace exists, anyone can grant such an account
roles. HelixAdmins should give platform-owned service accounts names without `--`,
and only grant roles to a `<workspace>--...` account when that workspace's Admins
are meant to hold its keys.
</Warning>

##### Service account restrictions

A workspace Admin can only use a service account whose existing keys and role
bindings all stay within the workspaces the new key is bound to. For example, with
a key already bound to `team-a`:

- A new key for the same account bound to `team-a` is allowed.
- A new key bound to `team-a` and `team-b` is allowed if you administer both, after
  you confirm the warning described below.
- An account that also has a role in `team-c`, or a key not bound to a workspace,
  is rejected with `403`. A HelixAdmin has to create or rotate keys for it.

The platform checks this when you create, rotate, or unsuspend a key, not
continuously. If the account later gains access elsewhere, the existing key keeps
working and you can still suspend or revoke it, but you can't rotate it, or
unsuspend it once suspended. A HelixAdmin is not subject to this check.

##### Confirming access for existing workspace-bound keys

Roles belong to the service account, not the key, so every key for an account gets
any role granted to that account. That includes keys bound to a workspace and
managed by that workspace's Admins. When the account has a live workspace-bound key,
the CLI warns you and asks you to confirm before you create a key that grants the
account a role it doesn't hold yet, in any workspace, whoever creates it. For
example, `Editor` in `team-a` when the account only has `Viewer` there, or any role
in `team-b` when it has none there.

A key that grants no roles, or only roles the account already holds (counting the
roles they include, such as `Viewer` for an account with `Editor`), needs no
confirmation:

```text
Warning: Service account 'team-a--otel-collector' already has live keys bound to
workspace(s) 'team-a', which those workspaces' Admins manage. Roles belong to the
service account, not the key, so those keys will also get the roles this key grants
that the account doesn't hold yet.
Create the key anyway? [y/N]:
```

Answer `n` to cancel without creating a key. Pass `--yes` to skip the prompt, for
example in scripts. Without a terminal, or when the output is captured (as in
`TOKEN="$(nemo auth access-keys create ...)"`), the command fails unless you pass `--yes`.
Revoked and expired keys don't trigger the warning. If the service account is
disabled, the command fails without a prompt; enable the account before you create
keys for it.

API clients get a `409` response with `code` set to `workspace_bound_keys_exist`
and a `detail` that names the service account and those keys' workspaces. To create
the key anyway, resend the request with `acknowledge_workspace_bound_keys` set to
`true`. The check runs again after the key is saved, so a key created at the same
time for the same account still triggers the `409` unless you confirmed; if both
need confirming, both do.

<Warning>
The warning only covers roles granted while creating a key. Adding the service
account as a member of another workspace with `nemo workspaces members create`
gives every key of the account, including workspace-bound ones, that access without
any warning.
</Warning>

##### Deleted and recreated workspaces

A key is bound to each workspace's ID; the name is only looked up when needed. If a
bound workspace is deleted and recreated under the same name, the new workspace's
Admins don't manage the key and only a HelixAdmin does. A HelixAdmin sees the old
workspace listed by its ID. The old key stays valid until a HelixAdmin revokes it,
because deleting a workspace doesn't revoke its keys. That also stops the recreated
workspace's Admins from reusing the service account: it was first issued a key before
their workspace existed, so only a HelixAdmin can grant it roles, in that workspace
or any other.

Roles belong to the service account, not the key, so a role you grant applies to
every key of that account. Rotating a key never changes roles.

A `--scope`-restricted key is enforced platform-wide, not just advisory: it can only
call endpoints whose required scope is covered by the services you listed (plus any
`platform:read`/`platform:write`-scoped endpoint). This includes the access-key
management endpoints themselves — a key scoped to `intake,entities` cannot create,
list, suspend, unsuspend, rotate, or revoke access keys unless `--scope` also includes
`auth`, which prevents a restricted key from minting itself broader access. This
applies even to a HelixAdmin's own scoped key: the HelixAdmin bypass only
grants access within the key's own scope, so a HelixAdmin who scopes down their
own key is still restricted by it, not granted unconditional access.

Rotate a personal key (one created without `--service-account`) by passing
`--rotate <jti>` with the prior key's `jti`: once the replacement key is
created and its requested workspace grants are provisioned, the referenced key
is revoked. `--rotate` only accepts a key you own that has no service account
bound to it.

List keys, temporarily suspend and restore one, rotate one, or permanently revoke one by
its stable `jti`:

```bash
nemo auth access-keys list
nemo auth access-keys list --page 2 --page-size 100
nemo auth access-keys suspend ak_0123456789abcdef0123456789abcdef
nemo auth access-keys unsuspend ak_0123456789abcdef0123456789abcdef
nemo auth access-keys rotate ak_0123456789abcdef0123456789abcdef
nemo auth access-keys revoke ak_0123456789abcdef0123456789abcdef
```

The list includes each key's `ACTIVE`, `EXPIRED`, `SUSPENDED`, `ROTATING`, or `REVOKED`
status plus its entity type, principal, description, issuer, audiences,
creation time, expiration time, and last authentication time. Regular users see
their own user-bound keys. HelixAdmins also see all service-account-bound keys,
including keys created by other admins. Suspension and revocation take effect on
subsequent authenticated platform requests. Use suspension to temporarily block
a key, such as while investigating suspected misuse, without permanently
revoking it. An unexpired suspended key can be restored with `unsuspend`. If the
key expires while suspended, `unsuspend` is a no-op and reports `EXPIRED`. A
revoked key cannot be restored.

`rotate` mints a successor key with the same name, description, and lifetime
characteristics, prints its token once, and transitions the original key to `ROTATING`.
The rotated-out key keeps authenticating for a dual-active grace period (configurable via
`auth.access_keys.rotation_grace_period_seconds`, 48 hours by default) so you can update
configuration or secret stores to the new key without downtime, then call `revoke` on the
old `jti` once traffic has moved over — check its last authentication time in `list` to
confirm no recent traffic before revoking. If you don't revoke it manually, it is treated
as revoked automatically once the grace period elapses. A key must be `ACTIVE` to rotate;
a suspended, already-rotating, expired, or revoked key must be resolved first.

### Token Inspection

Retrieve the raw JWT for debugging or use in other clients:

```bash
nemo auth token
```

Decode the token to inspect claims:

```bash
nemo auth token --decode
```

Key claims to check on OIDC tokens:

- `email` or `upn` — the principal identity
- `scp` or `scope` — granted scopes
- `exp` — expiry timestamp
- `iss` — issuer URL (must match your config)
- `aud` — audience (must match your config)

For Scoped Access Keys, check `sub`, `jti`, `nhx_token_type`, and
`nhx_access_key`. Service-account keys have `sub: service-account:<id>` and
`nhx_access_key.entity_type: SERVICE_ACCOUNT`.

## Token Management

### How Auto-Refresh Works

You never need to refresh tokens manually — the CLI and SDK handle it transparently:

- **SDK**: Refreshes lazily before each API call when the token is within 60 seconds of expiry. No background threads or timers — the cost is paid only when a refresh is actually needed (typically once per hour). Multiple `NemoClient.from_config()` clients in the same Python process share a single token, so only one refresh happens even with many clients.
- **CLI**: Checks the token before every command and refreshes if it expires within 5 minutes. To disable for a specific command: `nemo --no-auto-refresh workspaces list`.

Running multiple scripts or CLI commands simultaneously is safe — file-level locking prevents conflicts when refreshing tokens across processes.

If the refresh token itself has expired (e.g., after days of inactivity), re-login with `nemo auth login`.

### Manual Refresh and Logout

```bash
# Force a token refresh
nemo auth refresh

# Clear stored tokens
nemo auth logout
```

<a id="config-file"></a>
### Config File

Tokens are stored in `~/.config/nhx/config.yaml`:

```yaml
users:
  - name: default
    type: oauth
    token: "<access_token_jwt>"
    refresh_token: "<refresh_token>"
```

The OIDC token endpoint is **not** stored — it is discovered at runtime from your cluster's `/apis/auth/discovery` endpoint. This keeps the config portable across environments.

<Warning>

**Token storage security** — Access and refresh tokens are stored in plaintext. Protect this file:

- **File permissions**: Ensure `0600` (owner read/write only). The CLI sets this by default — verify after manual edits: `chmod 600 ~/.config/nhx/config.yaml`.
- **Shared directories**: Do not store in cloud-synced folders (Dropbox, OneDrive, Google Drive) or shared home directories.
- **Refresh token rotation**: Configure your IdP to rotate refresh tokens on each use. A stolen refresh token becomes invalid after the legitimate client uses it once.
- **Logout when done**: Run `nemo auth logout` on shared or temporary machines.

</Warning>
